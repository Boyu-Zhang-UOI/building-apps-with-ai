Build real software with AI, on a $0 budget. University of Idaho · CS [2xxx] · 3 credits · a 16-week semester · two 75-minute studios a week plus about 6 hours outside class · prerequisite: one programming course in any language.

1. Course description ​

In February 2025 Andrej Karpathy named a new way of making software: describe what you want to an AI, accept what it writes, run it, and keep going on "vibes". A year later the same people were calling the professional version agentic engineering, and a lot of vibe-coded apps had leaked their users' data.

This course teaches both halves. You will build and ship five working web projects by directing AI tools, starting in a chat window in week 1 and ending with an AI agent working inside your own repository in weeks 11–16. You will also learn the small set of habits that separate a demo from software you can trust: writing a spec before you prompt, writing the check before the code, working in small steps with git save points, testing, reading and explaining what the AI wrote, keeping secrets secret, and locking down your database.

You have already taken a programming course, so the course doesn't teach what a loop or a function is. It teaches what is new to most students: how the web works (HTML, CSS, JavaScript, servers and databases), the terminal, git, and how to direct an AI and check its work.

Every required tool has a free tier. The course is designed so that when a tool changes its limits (and they will), you switch to a fallback and keep working.

2. Who this course is for ​

  • Primary audience: students from any major (engineering, data science, business, the sciences, the arts and more) who have taken one programming course, usually in Python. You can write a loop and a function. You don't need to know HTML, CSS, JavaScript, the terminal, git or how the web works: the course teaches them, and the From Python to JavaScript page covers the differences that trip Python programmers up.
  • CS students who have completed CS 3383 Software Engineering: look at the upper-division course Engineering Software with AI (CS [4xxx]/[5xxx]) instead. It builds on what you already know.
  • Under 18, or in the EEA, the UK or Switzerland? Several free tools are 18+ only or can't be used to serve European users. Tell the instructor before the course starts, so the class can switch to an adjusted stack.

What you need: a laptop (Windows, macOS, Linux or ChromeOS) with a modern browser, a personal email address, your phone for two-factor sign-in, and a GitHub account. All coding happens in the browser through GitHub Codespaces, so you don't have to install anything. A local setup is optional (Optional: set up your own computer). The accounts are listed in Accounts.

3. Learning outcomes ​

By the end of the course you will be able to:

  1. Direct AI tools to build working web software, from single-file pages to a deployed full-stack app, using a repeatable workflow (the Safe Loop).
  2. Specify what you want before you build it: a one-page spec with user stories and testable acceptance criteria.
  3. Verify AI output instead of trusting it: write the check first, run it, test the happy path and edge cases, and read the diff.
  4. Explain every part of the code you submit, and debug a failing program by reading its error messages, with the AI switched off.
  5. Use version control (git and GitHub) as a safety net: commit, compare, revert, branch and review through pull requests.
  6. Build safely: protect privacy and secrets, keep API keys on the server, enforce database access rules, check dependencies, and contain AI agents.
  7. Ship projects to the public web and present them clearly.
  8. Adapt when tools change: choose between chat assistants, app builders, editor agents and terminal agents, and switch to a fallback without losing work.

4. How the course works ​

Two studios a week ​

Weeks 1–15 each have two 75-minute studios a few days apart (for example Tuesday and Thursday), plus about 6 hours of work outside class. Week 16 is finals week: there are no regular studios, and the Project Fair runs in the course's scheduled 2-hour final exam slot (Regulation H-1-b). Each week's README.md opens with a This week at a glance table: what to do before Studio A, what each studio covers, what's due, the AI rules and the minimum you need to keep up.

BlockTimeWhat happens
Studio A — Learn & build75 minRecap of last week's most-missed exit-ticket question (5 min) · concept talk (15 minutes at most) · live demo (10 minutes at most) · lab, core parts (about 40 min) · checkpoint share (5 min)
Studio B — Workshop75 minShow and tell (5 min) · lab continued, or a mini-lesson and practice on the week's second skill (about 40 min) · project work time, with oral-walkthrough slots in weeks 8, 12 and 14 and catch-up help (about 15 min) · debrief question (5 min) · exit ticket (10 min, 🔴 AI off)
Outside classabout 6 hPrep before Studio A (30 minutes at most: the week's README and at most one short reading) · homework core (about 3 hours) · project build time (about 2 hours) · PROMPTS.md and your weekly reflection on Canvas (about 30 minutes)

Some weeks move minutes between these blocks, but every studio stays 75 minutes, and the timed and AI-off activities (the Game in an Hour in week 3, the Debug Clinic in week 7, Be the Agent in week 11, the RLS Attack Lab in week 13 and the AI-off maintenance task in week 14) always fit whole inside one studio.

  • Due dates: homework is due before next week's Studio A (by default, 11:59 pm the night before). Canvas shows the exact time. Now and then a task that needs only Studio A's skills is due before Studio B; the week's page says so.
  • Core and stretch. Every lab part is marked Core or If time. Homework has a core tier (required) and a stretch tier (optional, never graded). Every homework ends with a Minimum to keep up box: the one thing you must have working before the next week.
  • Exit tickets are short questions with the AI off, once a week in weeks 1–14, normally at the end of Studio B (at the end of Studio A when a timed activity fills Studio B). From week 3, one question each week asks about a decision or function in your project from two weeks earlier, because remembering it later is what counts. They're graded on completion, not on correctness.
  • Oral walkthroughs (10 minutes each, 🔴 AI off) run in weeks 8, 12 and 14, during both studios' project time and in office-hour slots that week. Slots outside class time are scheduled at least two weeks ahead and announced in the first week; I cancel equivalent studio time to make room for them, and anyone with a conflict gets another time (catalog Regulation O-9-c). If you're not in a slot, you keep working on the lab.
  • Week 15 has no exit ticket and no walkthrough. University Regulation H-1-a says: "No quizzes or exams may be given in lecture-recitation periods during the week before finals week." So week 15 is for finishing your capstone, and week 16's Project Fair takes the place of a final exam.

The Safe Loop ​

Every lab from week 3 onward uses the same six-step loop (The Safe Loop):

#StepWhat you do
1DescribeState the goal, context, constraints and "done when". Check first: write the "done when" check before you ask for the code, in a separate prompt (from week 6, an automated test wherever the logic allows it)
2PlanAsk the AI for a plan. Edit it before any code is written
3StepBuild one small piece at a time
4TestRun it: your check, the normal case and at least one edge case, yourself
5ReadRead the diff. Keep only what you can explain. Teach back: before you commit AI-written code, write 2–3 sentences in PROMPTS.md saying what changed and why
6CommitMake a git save point with a clear message. Commits made with AI help end with an Assisted-by: [tool] line (taught in week 3, required from week 11)

Two-strikes rule: if two attempts to fix the same problem fail, stop. Start a fresh chat and rewrite your prompt with what you learned.

Why check first and teach back? Tests an AI writes after faulty code tend to agree with the faults (Konstantinou et al.), and students who had to explain AI code before adding it failed an AI-off maintenance task far less often than students who didn't (Sankaranarayanan). Being able to program already doesn't change this: experienced developers in one study were 19% slower with AI while believing they were faster (METR).

Three habits for talking to an AI ​

Taught in week 2 and used all course:

  1. Ask the AI to ask you questions first, before it builds anything.
  2. Show, don't describe: give it a picture, a sketch or a reference instead of a long description.
  3. Say what already works before you ask for a change, so it doesn't break it.

The Goldfish test (weeks 5 and 12) checks your documents the same way: paste only your SPEC.md (or AGENTS.md) into a fresh chat. If it can't understand or build from the document alone, without asking you, the document needs revising.

Week-by-week detail ​

Week 0 — Pre-work. Before Studio 1 (about 60–90 minutes, quick start): create your accounts, change the privacy settings, open a test Codespace, switch on GitHub Copilot, and get a first win: a one-line web page running in a chat assistant's preview. During week 1 (details): sign the safety contract on Canvas, take the pre-course self-assessment on Canvas, and apply for GitHub Education (verification can take several days, so start early). From Python to JavaScript (bridge page): the JavaScript differences that trip Python programmers up, such as === versus ==, const and let, braces instead of indentation, and null and undefined. Skim it in week 1 and keep it open.

Week 1 — Hello, Vibe Coding. What Karpathy meant, and why the field moved on. A mental model of LLMs: next-token prediction, context, non-determinism, confident mistakes. Privacy and the safety contract. In the studios: build a single-file personal page in a chat assistant with live preview; ask the AI to explain it section by section; change its HTML, CSS and JavaScript by hand (🔴 AI off); exit ticket. Outside class: finish the page, with one small feature you write entirely by hand (🔴 AI off); keep a note of the prompts that mattered and your hand changes; start the AI fluency pre-work; the week 0 tasks; reflection on Canvas. Understanding check: explain three parts of your page in plain English.

Week 2 — Ship Your Page. Publishing: repositories, GitHub Pages, and what "public" means for your files and their history. In the studios: publish your page on GitHub Pages; the three habits card; check your page's accessibility and fix what it finds; write your personal AI-use rules, version 1 (🔴 AI off, on Canvas); start PROMPTS.md; exit ticket. Outside class: improve the page using the three habits; PROMPTS.md (five entries); finish the AI fluency pre-work: Anthropic's free AI Fluency: Framework & Foundations course (a free sign-up; about 3 hours) or an equivalent your instructor names, with a short AI-free response on Canvas; reflection on Canvas. Understanding check: who can see your page, its files and its history?

Week 3 — Prompting & Save Points. Prompt anatomy (Goal · Context · Constraints · Done when). Why one giant prompt produces code you can't change later. Git basics: commit, history, diff, revert, and the Assisted-by: line. In the studios: practice the save-point workflow once, slowly (a four-part prompt, the diff, a commit with an Assisted-by: line, your history); exit ticket; then the timed Game in an Hour, built from a five-step plan with one commit per working step (graded on effort and save points, not on finishing), and a play-test swap. Outside class: finish the game; read Simon Willison's "Not all AI-assisted programming is vibe coding"; reflection. Understanding check: rewrite a weak prompt in four parts.

Week 4 — Undo, Compare, Explain. Save points make experiments safe, and an automated test checks your code for you. In the studios: a deliberate break-and-restore rollback; a two-model comparison; a peer explanation swap (🔴 AI off); your first automated test: a function from your game checked with node --test; the prompt makeover workshop; exit ticket. Outside class: add one more feature to your game in at least three save points, with a check written before each step; a restore drill; your game using the tested function in game/logic.js, with a test of your own passing; finish your prompt makeover (🔴 AI off for the rewrites); reflection. Understanding check: explain one function in a classmate's game.

Week 5 — Spec First. The one-page spec: problem, user, user stories, acceptance criteria in WHEN … THE APP SHALL … form, out-of-scope list, wireframe. Edge cases, and why AI-built apps miss them (the "70% problem"). In the studios: write the SPEC.md for Project 1 (🔴 AI off for the first draft); a peer spec review (written up on Canvas); the Goldfish test of your spec, then revise it; exit ticket. Outside class: revise your spec; TESTS.md with a manual test for every MUST criterion and a plan for your logic; your first automated test for Project 1, written before its code, so it fails for now (check first); your written spec review on Canvas; reflection. Understanding check: turn a vague requirement into a testable criterion.

Week 6 — From Spec to App. Browser app builders, what they generate, lock-in and credit budgets. Your app's rules as pure functions in their own module. In the studios: the builder bake-off as a jigsaw: each student runs one builder on their own spec and scores it, then pairs compare scorecards; start Project 1 in a Codespace in Safe Loop order, checking first with an automated test where the logic allows it, and previewing every change before you commit it (if the page goes blank, open the Console); exit ticket. Outside class: Project 1 v1 live, with at least half of its MUST criteria working and at least one automated test passing; an acceptance table in the README. Your bake-off Verdict (🔴 AI off, on Canvas) is this week's reflection. Understanding check: which acceptance criteria fail, and why?

Week 7 — Read It, Debug It. Anatomy of a web app (structure, style, behavior, state, storage). Browser DevTools, error messages and the scientific method of debugging. In the studios: map your own Project 1 and find planted errors in it with DevTools (an error drill, 🔴 AI off); exit ticket; then the Debug Clinic: planted bugs, about an hour with the AI off (🟡 hint-only tutor mode after 10 minutes stuck on one bug), then a debrief. Outside class: check your own Project 1 for the clinic's five bugs (🔴 AI off); TESTS.md with at least three edge cases; fix what your acceptance table says fails; reflection. Understanding check: find the failing line from an error message.

Week 8 — Own It. You own the code you can explain, change and test. In the studios: practice git log, git diff and git revert (🔴 AI off), then write tests for Project 1's logic while oral walkthrough 1 slots begin; "You write it": write a function yourself from a short spec, test first (a code skeleton with blanks is a hint if you need one, not the starting point); exit ticket. Outside class: Project 1 final, with at least three automated tests of its pure logic passing with node --test; TESTS.md complete; the mid-course survey; reflection. Project 1 due.

Week 9 — APIs & Secrets. Requests, responses, JSON and APIs. Client versus server: anything sent to the browser is public. API keys, environment variables, .gitignore, free-tier rate limits, and why a public endpoint that spends your key needs limits. Not every key is a secret: some are public by design and safe only with access rules. In the studios: trace one request through the starter AI micro-app yourself; a free LLM API key kept in .env; run it in your Codespace; make it your own (its job and its page); exit ticket. Outside class: your app's own job, page and input limit, with each error tried on purpose; a first draft of your capstone pitch; reflection.

Week 10 — Servers & Deployment. A production URL, a provider you can swap, and proof that the key stays secret. In the studios: deploy to Vercel and check the production URL; the provider-swap drill (change configuration only); prove the key is secret (DevTools, and a secret scan that also checks your git history); a mini-lesson on external public APIs (a server route that calls a public API needing no key); exit ticket. Outside class: micro-app live; a "Where the key lives and who can read it" README section (🔴 AI off; it takes the place of this week's reflection); at least two validation tests that you write yourself; a hidden-costs checklist; your capstone pitch. Rewriting the rate-limit message is stretch. Micro-app due; capstone pitch due 72 hours before week 11 Studio A.

Week 11 — How Agents Work. An agent is an LLM in a loop with tools. Context as working memory, plan-first prompting, approval modes and sandboxes, and how agents fail (fake success, deleted files, loops). AGENTS.md is advice, not enforcement: what actually protects you is the Codespace, approval prompts, narrowly scoped keys, spending caps and database rules. Approvals stay on; never use autopilot or skip-permissions modes. In the studios: Be the Agent; open your capstone repo (created from the starter before class); write SPEC.md for today's one criterion and an AGENTS.md with a Scope section; build your first feature with an agent, checking first and teaching back; exit ticket. Optional, if you program comfortably: read (don't write) a minimal agent loop. Outside class: finish your first feature on its own branch (not merged yet); a trace of your agent's run (🔴 AI off); complete SPEC.md; deploy early; agent log in PROMPTS.md; reflection.

Week 12 — Pull Requests & Agent Code. Branches and pull requests, and reading agent-written code before you trust it. In the studios: a mini-lesson on branches and pull requests (add one test by hand, then open a pull request, review it yourself and merge it); find a planted bug in agent-written code (🔴 AI off); feature clinic stations, where you pick what your capstone needs: a simple chart, or an external API; oral walkthrough 2 slots; exit ticket. Outside class: the Goldfish test of your SPEC.md; the AGENTS.md trial (two small tasks: did the agent follow the file? make one change); one more feature as a pull request with a test; reflection. Milestone 1 (milestones).

Week 13 — Data & Access Rules. Authentication versus authorization; row-level security (RLS); publishable versus secret keys; database permissions ("grants") always together with RLS. 2026 case studies: thousands of databases with publicly readable tables, and a platform that let anyone read other users' projects (case studies). In the studios: the RLS Attack Lab, using the attack page hosted on the course website; a worked example of connecting your app to Supabase (the project URL and publishable key in public/config.js, grants and RLS policies), then an attack on your own table; connect one feature with the agent; exit ticket. Outside class: your second feature type working at the production URL, merged through a pull request (Supabase with RLS and supabase/policies.sql, or another feature type); section 3 of SECURITY_CHECKLIST.md with evidence; reflection. From this week to the Fair, open your capstone database at least once a week: free databases pause when nobody uses them.

Week 14 — Security & Review. Cross-site scripting; secrets in old commits; slopsquatting; prompt injection and the "lethal trifecta". 2026 case studies: an agent that deleted a production database and its backups, agents that published private screenshots, and malware that hunts for AI keys (case studies). In the studios: a 7-minute prompt-injection demonstration by the instructor; a security sweep (secret scan including history, npm audit, a package check, an XSS test); a one-paragraph threat model of one feature; exit ticket; then an AI-off maintenance task on your own capstone (30 minutes, 🔴 AI off) and peer review as a pull-request review, plus your written review on Canvas (🔴 AI off), then compared with an AI's review. Oral walkthrough 3 slots run alongside. Outside class: SECURITY_CHECKLIST.md with evidence, and its threat model; respond to your review; the handoff test (a partner tries a change using only your README and AGENTS.md); reflection. Milestone 2.

Week 15 — Ship It. Definition of done, polish, accessibility basics, telling the story of a project, and where the field is going. In the studios: polish sprint (accessibility; empty, loading and error states; a README with an honest Known issues section); a final security pass; record a 2–3 minute demo video; rehearse your Project Fair pitch. No exit ticket and no walkthrough (Regulation H-1-a). Outside class: finish the polish checklist and bring every document up to date; link your demo video; reflection. Due before the Project Fair.

Week 16 — Project Fair (finals week). No regular studios. The Project Fair runs in the course's scheduled 2-hour final exam slot (Regulation H-1-b): you demo your capstone and try your classmates' apps. At the Fair: the post-course self-assessment (🔴 AI off, on Canvas) and the course retrospective. Taking part counts like a studio, with a make-up for absences under Regulations M-1 and M-3. Final submission: the production URL and a screenshot, a v1.0 release and the demo video are due at the start of the Project Fair; your revised personal AI-use rules and your final reflection (🔴 AI off, on Canvas) are due by 11:59 pm on the last day of finals week.

Six skills you must be able to show without AI ​

These are checked in the oral walkthroughs, and practiced in the exit tickets (Six Skills You Must Show Without AI). Each needs to be shown only once, and you get several chances.

Late work ​

You have two grace tokens, each extending one deadline by 48 hours with no reason needed. After that, late work loses 10% of its points per day for up to three days. Tokens can't be used for live events (studios, exit tickets, walkthroughs, the Project Fair), which have make-up rules instead (section 11). Running out of free credits is not by itself a reason to be late, because switching to a fallback is part of the course. Full rules: Late work and grace tokens.

Pass/fail ​

This course is letter-graded. If you're eligible, you may take it under the University's pass/fail option (catalog Regulation B-10-a). Talk with your advisor first. You need a cumulative GPA of 2.00 or higher (unless it's your first university-level term); you may take one such course a semester, and no more than 12 such credits count toward a bachelor's degree. The option isn't open for courses in your major or major subject field, courses your curriculum or college requires, or general-education courses. The deadline to switch is early in the term: see the Registrar's dates and deadlines. I'm not told who chose it: I report a letter grade, and the Registrar records a C or higher as P. For undergraduates, a D stays a D (B-10-d).

Incompletes ​

Apart from the academic-integrity case in section 11 (FSH 2300 F-9), an Incomplete (I) is possible only under catalog Regulation F: you have been attending and doing passing work until near the end (the regulation's cutoff is three weeks before the close of the semester), and an extenuating circumstance, such as serious illness or a death in the family, makes it impossible to finish on time. We agree it together, I set out in writing what's left to do and by when, and I record a grade that applies if the work isn't completed. Running out of time because of procrastination doesn't qualify. You must finish by the Regulation F-2 deadline (the last day of the following summer for a fall Incomplete, the last day of the following fall semester for a spring or summer one); otherwise the I changes automatically to the grade I recorded. You can't graduate with an I on your record (F-3). If something serious happens, talk to me as early as you can.

8. AI use policy ​

This course requires AI. The rule is not "how much AI did you use" but "can you explain what you shipped". Every task is labeled with one of three levels, always in words as well as color.

LevelWhenThe complete list
🟢 AI onBuilding, explaining, learningGenerating code; asking for explanations, plans and reviews of your diffs; debugging outside the Debug Clinic; translating instructions into your own language. Everything not listed below is 🟢 AI on
🟡 AI limitedWhere the goal is your own thinkingYour SPEC.md (Project 1 and capstone): the AI may ask questions, critique it and run the Goldfish test, but you write it. Your capstone pitch: critique only. The Debug Clinic (week 7): AI off, then hint-only tutor mode after 10 minutes stuck on one bug. "You write it" (week 8): the AI may plan and review, but you write the code. Any other task a brief marks 🟡 AI limited follows that brief
🔴 AI offChecks of your understanding, and writing addressed to peopleExit tickets · oral walkthroughs, retakes, skill follow-ups and "explain it" conversations · weekly and final reflections, including the week 6 bake-off Verdict · written peer reviews (an AI review may come after yours, to compare) · peer explanation swaps · the pre- and post-course self-assessments · your personal AI-use rules (week 2, revised in finals week) · your response to the AI fluency pre-work · the first draft of your Project 1 spec (week 5) · the hand-made code changes and the feature you write by hand in week 1 · the prompt-makeover rewrites (week 4) · the micro-app's "Where the key lives and who can read it" section (week 10) · the AI-off maintenance task (week 14) · the teach-back notes and the "What I wrote or decided myself" section of PROMPTS.md · a pair's contribution statement · any other task a brief marks 🔴 AI off

If two labels ever seem to disagree, follow the stricter one and ask. Using AI on 🔴 AI-off work, or beyond what a 🟡 AI-limited label allows, is academic dishonesty under the University's Student Code of Conduct (section 11).

  • Disclose: every project has a PROMPTS.md with your key prompts, links to exported chats where possible, notes on what you changed, and teach-back notes for AI-written changes. Commits made with AI help end with an Assisted-by: [tool] line.
  • Own it: "If you can't explain it, you didn't build it." You may be asked to explain any line you submit.
  • Credit others: if you use code, images or text from a person or website, credit it in your README. Using prompts you found online is fine; say where they came from.
  • Your own rules: in week 2 you write a few personal rules for when you will and won't use AI, and in finals week you revise them. Students who set their own rules tend to do better (Azimi).

The safety contract ​

Before Studio 1 you set your privacy settings and skim the safety contract; you sign it on Canvas during week 1. Each rule starts the week it's taught, and the course sets up the protections around you (a Codespace sandbox, starters that keep keys off the browser, a secret scanner). In short:

Privacy of your work ​

Your projects are public on purpose: they become your portfolio. Your grades and personal writing are not. University policy treats grades and graded work as private (FSH 4700 F-6, and FSH 2600, which applies FERPA, the US federal student-records law), so:

  • In your public repos, under your GitHub username: code, SPEC.md, TESTS.md, PROMPTS.md, AGENTS.md, SECURITY_CHECKLIST.md and READMEs.
  • On Canvas only: reflections, exit tickets, your personal AI-use rules, the signed safety contract, self-assessments, written peer reviews, pair contribution statements, the capstone pitch, and all grades and feedback.
  • Never commit grades, feedback, reflections, classmates' real names (use GitHub usernames), your student ID, or real personal data about anyone. You don't need your real name anywhere public.

11. Course policies ​

Attendance and participation ​

Studios are where most of the learning happens, and they count for 15% of your grade (30 studios, two a week in weeks 1–15, each scored out of 10 for lab work, peer explanation, and the checkpoint or exit ticket; the Project Fair in finals week is scored the same way). Your lowest four of these scores are dropped, which covers a few ordinary missed days. Missing more than that lowers this component, and missing a walkthrough or the Project Fair affects those items too. You're responsible for catching up on what you missed: each week's lab is written step by step, and the studios' project-work time and office hours are there for catch-up help.

Missed studios and make-up work ​

  • Absences the University recognizes (catalog Regulation M-1): official university activities, your own illness, family illness or care, or other compelling circumstances. Tell me as soon as you can (before the absence, for official activities). You can make up the studio for full credit within one week: do the lab's core parts and, for the studio with that week's exit ticket, the exit ticket on Canvas. Missed walkthroughs are rescheduled without penalty.
  • Religious observance (Regulation M-3): walkthroughs, exit tickets and the Project Fair are rescheduled. Tell me as early as you can.
  • Other absences: do the lab and (for the studio with the exit ticket) the exit ticket within 48 hours for up to 7 of the 10 points.
  • Online or in another time zone for part of the course? Talk to me in week 1, so we can set up the online arrangements.

Full rules: Absences and make-up work. All three oral-walkthrough windows are posted on Canvas in week 1.

Recording of class sessions ​

Students may record studios only with my consent or as an approved CDAR accommodation, and in either case must tell me first (FSH 4700 F-8). Concept talks I record are posted only on Canvas. Oral walkthroughs are recorded only with your consent, kept where only staff can see them, and deleted once grades are final.

Academic integrity ​

Disclosure is the rule. Honest disclosure of AI use in PROMPTS.md is never penalized, even when the AI did most of the typing.

The University of Idaho Student Code of Conduct and Resolution Process (FSH 2300) applies. In this course, academic dishonesty includes: using AI on 🔴 AI-off work or beyond a 🟡 AI-limited label (the Code names "reliance on prohibited technological assistance/artificial intelligence tools", FSH 2300 E-1.c); fabricating evidence such as test results, security evidence or PROMPTS.md entries; submitting someone else's code, prompts or writing as your own; reusing work from another course without both instructors' approval; and having someone else take your walkthrough or exit ticket.

There are two separate processes, and they never mix:

  1. "Explain it or redo it" is a learning conversation, not a sanction. If you can't yet explain part of your own work, we talk for about 10 minutes. If you still can't, you redo that part within 7 days and it is graded on the normal rubric, with no penalty.
  2. Suspected academic dishonesty goes through the University's process. If I suspect it, I will tell you and report it to the Dean of Students, as FSH 2300 requires. No grade consequence is applied until that process has concluded and its decision has been communicated to you; if grades are due before then, an Incomplete is entered until it is resolved (FSH 2300 F-9). If the University's process finds you responsible, the most I can apply as an academic consequence is an F in the course (catalog Regulation O-2). The Dean of Students explains your options and rights.

The course doesn't use AI detectors. Full details: Academic integrity.

Learning civility ​

In any environment in which people gather to learn, it is essential that all members feel as free and safe as possible in their participation. Everyone in this course is expected to be respectful and civil to one another in discussion, in action, in teaching and in learning. If our class interactions fall short of that, please talk with me; you can also contact the Dean of Students (208-885-6757), the Counseling and Mental Health Center's confidential services (208-885-6716), or the Office of Civil Rights and Investigations (208-885-4285). See also FSH 4170 (Maintaining Instructional Order).
