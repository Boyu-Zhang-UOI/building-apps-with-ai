Project 1: A Tool I'd Actually Use (weeks 5–8) ​

Build a small web tool you will really use, from a spec you wrote yourself, in plain HTML, CSS and JavaScript you can read. Then prove it works, with tests.

The brief ​

Pick a small, everyday problem that you have. Write a one-page spec for a tool that solves it. Use AI to build it from that spec, then make it yours: read it, test it, fix it and write one function yourself.

The tool must:

  • do at least three different things for its user (for example add an entry, mark it done, and show a summary);
  • be single-user: one person, one browser, no accounts;
  • save its data in the browser with localStorage, so it's still there after a reload;
  • be written in plain HTML, CSS and JavaScript that you can open and read;
  • keep its pure logic (the rules, as functions that take inputs and return a result) in its own file, with at least three automated tests;
  • be live on GitHub Pages.

Why this project ​

  • You are the user. When you use your own tool, you notice bugs and missing features, and you care about fixing them. Courses that have learners build tools around their own lives use exactly this idea (Coursera: Build Anything with AI).
  • The spec comes first. AI builders get you most of the way fast, then stall on edge cases. Addy Osmani calls this the "70% problem". A spec with testable criteria tells you exactly what the last 30% is. In a 2026 study, students' writing skill predicted how well they vibe-coded (Thorgeirsson et al.), so the spec is a core skill, not paperwork.
  • Edge cases are where the grade is. When researchers watched students vibe code, only 2.2% of their tests tried edge cases, and none wrote a unit test (Geng et al.). This project makes you check the unusual cases on purpose, and test your tool's logic automatically.
  • Plain files you can read. In week 8 you will debug this code with the AI switched off, in oral walkthrough 1. That is only fair if the code is small and readable, so no frameworks.

What "single-user" and localStorage mean ​

localStorage is a small storage box that each browser keeps for each website. Your tool can save text there and read it back after a reload.

  • The data stays in that one browser on that one device. If you open your tool on your phone, it starts empty.
  • Other visitors to your live site each get their own empty box. They can't see your data, and you can't see theirs.
  • Clearing the browser's site data deletes it.

That's why this project is single-user: there is no server and no shared database. Sharing data between people needs a server and access rules, which you will learn in weeks 9–13.

Requirements ​

Everything on this list must be in your final submission.

The tool

  • ☐ At least three distinct features, matching the MUST stories in your spec.
  • ☐ Files: index.html, style.css, app.js (the only file that touches the page and localStorage), your pure logic as modules in lib/ that app.js imports, your tests in tests/, and a package.json that makes npm test run node --test. No frameworks, no npm packages, no build step.
  • ☐ Data is saved in localStorage and survives a page reload.
  • ☐ Live on GitHub Pages.
  • ☐ One function that you wrote yourself in week 8 ("You write it"): pick a feature card and write its function by hand from the card's short spec. A code skeleton with blanks is there as a hint if you need one. The AI may plan and review, but you write the code. Name the function in PROMPTS.md.

The documents (all at the top level of the repo)

  • ☐ SPEC.md, written by you from the SPEC template, with at least 5 acceptance criteria in the form WHEN … THE APP SHALL …, including at least 2 edge cases, revised after your Goldfish test (below).
  • ☐ TESTS.md, from the TESTS template, with a manual test for every acceptance criterion, including at least 3 edge-case tests, each with a dated result.
  • ☐ At least three automated tests of the tool's pure logic: tests of pure functions (ones that only take inputs and return a result, without touching the page or localStorage), in a tests/ folder, passing with npm test (node --test). At least one tests an edge case. From week 6, write each test before you ask for the code it checks (check first). Paste the output in TESTS.md.
  • ☐ PROMPTS.md, from the PROMPTS template: your key prompts, what went wrong, your Goldfish test, short teach-back notes on AI-written changes (2–3 sentences: what changed and why), and what you changed or wrote yourself.
  • ☐ README.md, from the project README template, with the live URL, an acceptance table ("Status against the spec") that matches what the tool really does, and an honest Known issues list.

The history

  • ☐ At least 6 commits with messages that say what changed. One giant "upload files" commit doesn't show your process. Commits made with AI help can end with an Assisted-by: [tool] line (taught in week 3, required from week 11).

The app builders in week 6 are for learning what they do well and badly. You keep plain files because you need to be able to read and debug them in weeks 7 and 8. The week 6 lab shows one way to do this: hand your SPEC.md to a chat assistant and ask for plain HTML, CSS and JavaScript files only.

Preview before you commit ​

From week 6 you build in a Codespace, and you look at the result before you commit it, in Safe Loop order: describe (with the check written first), plan, one small step, test it in the preview and with node --test, read the diff, then commit. To preview, run this in the Codespace terminal and open the forwarded port:

bash
python3 -m http.server 8000

Blank page in the preview? Open DevTools (F12, or right-click → Inspect) and look at the Console tab. A red error usually names the file and line that broke.

Repository layout ​

Your reflections, your bake-off Verdict and your peer review go on Canvas, not in the repo (why).

Your SPEC.md ​

🟡 AI limited: you write the spec. Write the first draft with the AI off (week 5). After that the AI may ask questions and critique it ("What is ambiguous? Which edge cases am I missing?") but not write it. A good example: example spec.

Aim for acceptance criteria that anyone could check by using the tool:

WeakStrong
The list should handle empty input nicely.WHEN I press Add with an empty box, THE APP SHALL add nothing and SHALL show "Please type something".
It remembers my stuff.WHEN I reload the page, THE APP SHALL show the same entries in the same order.
Works on phones.WHEN the screen is 375 pixels wide, THE APP SHALL show every button without sideways scrolling.

Edge cases are the unusual-but-possible situations: empty input, very long input, duplicates, special characters, reloading, a small screen, the first visit when nothing is saved yet.

The Goldfish test. Paste only your SPEC.md into a fresh chat (no other context) and ask what it would build. If it has to ask you questions, or gets something wrong, the spec isn't clear enough yet. Log what it asked or got wrong in PROMPTS.md, and revise the spec. The rubric gives credit for the revision.

If your plans change while you build, update the spec and its "Last updated" date. A spec that matches the tool is worth more than a spec that matches your first idea.

Your TESTS.md ​

  • Write one manual test per acceptance criterion: numbered steps and the expected result.
  • At least three tests must be edge cases. Mark them "(edge case)".
  • Run every test and record the date and the result. A test that failed, and then passed after a fix, is the best evidence you can show. Log it under "Bugs found by testing".
  • Try typing <b>hi</b> as input. If the text shows up bold, your tool is treating typed text as code; ask the AI why, and fix it (the usual fix is textContent instead of innerHTML).
  • Add your automated tests (at least three): what each one checks, and the node --test output.

Your README ​

Start from the project README template. For this project:

  • In Run it yourself, replace the npm commands with: open the live site; or, in a Codespace, run python3 -m http.server 8000 and open the forwarded port. To run the tests: node --test.
  • In How it works, the data row is localStorage, with the key name you used.
  • Authorization is enforced in: "n/a: single-user tool, data stays in your own browser."
  • The Status against the spec table lists every acceptance criterion as passing, partly passing (say what's wrong) or failing. Honest beats perfect.
  • Known issues: anything that doesn't work yet, or works only partly. Naming a real limitation never costs points.

Is it the right size? Too small: it does one thing, like a calculator with one button. Too big: it needs accounts, sharing between people, a server, an API key or live data from the internet. Those belong in weeks 9–16, and some make great capstone ideas (capstone ideas).

About personal data: anything about other people (housemates, friends) goes in as nicknames or "Person A". Your own data stays in your own browser, but the repo is public, so never commit real entries in your code or screenshots.

How it's graded ​

The Project 1 rubric puts most of the points on your spec, your tests and your process. Whether the tool works counts, but it is only one row. Oral walkthrough 1 (week 8) uses this project: you'll explain a function, find a failing line from an error message, make a small change and revert a commit, with the AI off.

Submit ​

Follow How to submit: on Canvas, the repo URL, live URL and the link to your final commit, for v1 and again for the final version.

If you get stuck ​

  • The builder's output is React or has many files you don't understand: don't keep it. Use the bake-off to learn, then ask a chat assistant to build from your SPEC.md in plain HTML, CSS and JavaScript only.
  • Blank page: open the Console in DevTools and read the red error (see Preview before you commit).
  • Data disappears on reload: open DevTools → Application → Local Storage and check whether anything is saved. Ask the AI to explain its save and load code line by line. The web basics page explains DevTools.
  • Two failed fixes in a row: the two-strikes rule. Go back to your last good commit and start a fresh chat.
  • Your v1 doesn't work by week 7: talk to your instructor about the rescue starter, a working tool you can continue from so you can still take part in weeks 7 and 8.
  • Out of credits: I ran out of free credits.
