Home Page (weeks 1–4) ​

Your first project: a personal page, built in week 1 and live on the public web by the end of week 2, with a browser game added in weeks 3 and 4. It becomes the portfolio that links to everything else you build.

What you'll build ​

  1. Weeks 1–2: a personal page. One HTML file that says who you are, what you're learning and what you're building. You make it with a chat assistant in week 1 and change parts of it by hand, then publish it in week 2 with GitHub Pages (GitHub's free hosting for static websites) from a repository (a project folder that git tracks).
  2. Weeks 3–4: a game. A small browser game in a game/ folder of the same repo, built in the timed Game in an Hour in week 3, one working step at a time, with a commit (a git save point) after each step. In week 4 you break it and restore it on purpose, compare two models on it, and add one more feature.

Why this project ​

Most vibe-coding courses start the same way, with a small single-file page you can publish on day one (landscape report). A live page in the first two weeks proves that you can make real things. The game in weeks 3 and 4 proves that the method works on something new, and it gives you instant visual feedback with no server to worry about.

Keep it simple. The point of this project is the loop (describe, generate, run, change, commit, publish), not a perfect design.

Weeks 1–2: the page ​

Requirements

  • ☐ One file, index.html, at the top level of the repo. Styles go inside a <style> tag in that file; any script goes inside a <script> tag.
  • ☐ Built with a chat assistant that shows a live preview. Afterwards, ask the AI to explain the page section by section, and read the explanation.
  • ☐ A <title> and a main heading with your name or a display name you choose.
  • ☐ At least three sections, for example "About me", "What I'm learning" and "Projects". The Projects section is where you will add links later.
  • ☐ Small code changes you made by hand in week 1, typed yourself without AI help, in the HTML, the CSS and the JavaScript, plus one small feature you wrote entirely yourself (for example a button that switches the color theme or shows and hides a section). Note them in PROMPTS.md under "What I wrote or decided myself".
  • ☐ Any image has alt text (a short description in the alt="..." attribute, read aloud by screen readers), and you've done the week 2 accessibility check and fixed what it found.
  • ☐ Published in week 2: a public repo named exactly [username].github.io, with GitHub Pages turned on, so the page loads at https://[username].github.io/.
  • ☐ A PROMPTS.md file in the repo (started in week 2 from your week 1 notes), copied from the template, with your most important prompts and what you changed.
  • ☐ Ready for the week 1 exit ticket: you can explain three parts of your page in plain English.

When you improve the page in week 2, try the three habits from the week 2 habits card: ask the AI to ask you questions first; show it a picture or a page you like instead of describing it; and say what already works before you ask for a change.

✅ Checkpoint: you open https://[username].github.io/ in a private window, on your phone or a friend's, and see your page. (A new Pages site can take a few minutes to appear.)

Weeks 3–4: the game ​

Pick a game from the game menu, or propose your own of similar size.

Requirements

  • ☐ The game is one file, game/index.html, in the same repo as your page. It loads at https://[username].github.io/game/.
  • ☐ Built in week 3 from a five-step plan, with one commit per working step. Each commit message says what works now, for example Step 3: ball bounces off the paddle.
  • ☐ One deliberate break and restore (week 4). Make a change that breaks the game, commit it, then put the last working version back as a new commit. Your history shows the bad commit and the restore commit. (This is what the git command git revert does; you'll practice the real command in week 8.)
  • ☐ A two-model comparison (week 4). Give the same prompt to two chat assistants and note in PROMPTS.md which result was better, and why.
  • ☐ Your first automated test (week 4): one function from your game moved into game/logic.js, with tests in tests/logic.test.js that you write first and see fail, then pass with npm test (which runs node --test). Your game uses the tested function, and one of the tests is your own.
  • ☐ One more feature after the timed build, planned first and built in at least three save points (commits), with a check written before each step (week 4).
  • ☐ Your home page links to the game from its Projects section.
  • ☐ PROMPTS.md has a section for weeks 3 and 4.
  • ☐ Ready for the week 3 exit ticket and the week 4 explanation swap: you can explain one function in your game (and in a classmate's).

The Assisted-by: line. In week 3 you learn to end a commit message with a line naming the AI tool that helped, for example:

text
Step 4: add a score that resets on restart

Assisted-by: [tool]

Try it on your game commits. It becomes required in week 11.

✅ Checkpoint: the history of game/index.html on GitHub shows one commit per working step, one bad commit and one restore commit.

Repository layout ​

A README.md is optional here. Later projects each get their own repo. The exact homework items are in the homework checklists for week 1, week 2, week 3 and week 4.

Not in this repo: your reflections, the signed safety contract, your personal AI-use rules and your self-assessment. They go on Canvas, the course's learning management system, where only you and the course staff can read them (why).

Privacy: a public page is really public ​

Search engines can find your page, and every old commit stays visible.

  • Don't publish your phone number, home address, date of birth, student ID or anything you'd put on a password-reset form.
  • A first name or a nickname is fine. So is leaving out a photo.
  • Only use images you made or have permission to use, and credit them (for example, "Photo by [photographer] on Unsplash") in a small Credits section at the bottom of the page.
  • Don't put other people's names or photos on your page without asking them, and never name classmates.

Done when ​

  • ☐ The page and the game both load from their live URLs in a private window.
  • ☐ Everything on the two requirement lists above is ticked.
  • ☐ You have submitted the repo URL and live URL on Canvas (how to submit).

Stretch ideas (optional) ​

  • Make the page look good on a phone (ask the AI for a "responsive" layout, then test it by making your browser window narrow).
  • Add a high score to your game that survives a page reload (hint: ask about localStorage).
  • After each later project, add its live link to your Projects section. By the Project Fair this page is your portfolio.

If you get stuck ​

  • The page doesn't appear at the URL: check that the repo is public, the file is called index.html (all lowercase) and sits at the top level, and Pages is turned on in the repo settings. Then wait a few minutes. Menus move; if you can't find the Pages setting, ask your chat assistant where it is.
  • A blank page: open DevTools (F12, or right-click → Inspect) and look at the Console tab. A red error usually names the line that broke.
  • The AI's code doesn't work: use the two-strikes rule. After two failed fixes, start a fresh chat with a better prompt.
  • Your chat assistant hit a limit: switch to the fallback in Tool Handout. See I ran out of free credits.
  • Git confuses you: see the git cheat sheet and GitHub basics.
