The Safe Loop ​

Print this page. Keep it next to your keyboard. Use it in every lab from week 3 onward.

Vibe coding in its original form means accepting whatever the AI writes without reading it. That is fine for a throwaway toy. For anything you want to keep, share or trust, professional developers who work with AI converge on the same short loop. This course calls it the Safe Loop.

The six steps ​

The Safe Loop is six steps done in order. After step 6 you go back to step 1 for the next small change, so the steps form a circle: Describe → Plan → Step → Test → Read → Commit, then Describe again. Two habits sit inside the loop: check first (end of step 1) and teach back (end of step 5).

  1. Describe. Say what you want: goal, context, constraints, and how you'll know it's done. Then check first: write down the check that proves it works (from week 6, an automated test where the logic allows it), in a separate prompt, before you ask for the code.
  2. Plan. Ask for a plan before any code, and edit it.
  3. Step. Ask for one small change.
  4. Test. Run it: your check, the normal case and at least one edge case.
  5. Read. Read the diff and keep only what you can explain. Then teach back: write 2–3 sentences in PROMPTS.md saying what changed and why.
  6. Commit. Make a save point with a message that says what changed, plus an Assisted-by: line if AI helped. Then go back to step 1.

Check first ​

What: write the check for a step before you ask the AI to build it, in a separate prompt (or a separate chat) from the one that writes the code.

  • Weeks 1–5: the check is the "Done when" line, written as things you will try by hand: "Clicking Clear, then OK, empties the list. Reloading keeps it empty. Clicking Cancel changes nothing." Write it in your prompt or in your README's acceptance table before you ask for code. You write your first automated test in week 4, as practice.
  • From week 6: the check is an automated test wherever the logic allows it: a small file in tests/ that npm test (or node --test) runs. Write it yourself, or ask the AI for it in its own prompt that contains only the "Done when" line and the name of the function, not the code. Use the check-first test prompt. Things you can only judge by looking, such as a layout or a color, keep a written check you try by hand.
  • Run the test before the code exists. It should fail (red). After the step, it should pass (green). This is red/green testing.
  • Never let the AI change a test to make it pass. One developer reported a "fix it" prompt that changed a test's expected status code from 200 (success) to 500 (server error), so the broken code "passed" (Hacker News). If a test seems wrong, decide yourself, and say why in PROMPTS.md.

Why: when an AI writes tests after it has written faulty code, the tests tend to agree with the faults. In one 2026 study, tests generated after buggy code caught 14% of the faults, against 25% for tests written independently (Konstantinou et al.). A check you write first, apart from the code, is a real check.

Teach back ​

What: before you commit AI-written code, write 2–3 sentences in PROMPTS.md, in your own words: what changed, why it works, and what you'd look at first if it broke. 🔴 AI off: write it yourself. A teach-back the AI wrote for you doesn't count (AI use policy).

markdown
**Teach-back:** The agent added a `clearAll()` function in app.js. It calls `confirm()` first,
then empties the `todos` array and saves it to localStorage, and the list is redrawn from that
array, so an empty array means an empty list. If it broke, I'd check the localStorage key is still "todos".

If you can't write the teach-back, you're not ready to commit: ask the AI to explain the diff (explain this code), read it again, and then write it.

When: for every AI-written change you keep. From week 11, a teach-back before every agent commit is part of the capstone Process grade (rubric). The teach-back prompt can check your sentences against the diff after you've written them.

Why: in a 2026 study of 78 learners, 77% of those who had used AI without restrictions failed a 30-minute maintenance task once the AI was switched off, against 39% of those whose tool had required a short explanation before generated code could be added (Sankaranarayanan). The teach-back is that explanation step.

The Assisted-by line ​

What: a commit made with AI help ends with a line naming the tool, separated from the message by a blank line:

text
Add clear-all button with confirmation

Assisted-by: GitHub Copilot

  • In the Source Control box (github.dev or a Codespace): type the message, press Enter twice to start a new paragraph, then type Assisted-by: [tool]. Commit as usual (the commit button, or Ctrl+Enter / Cmd+Enter).

  • In the terminal, a second -m adds the line as its own paragraph:

    bash
    git commit -m "Add clear-all button with confirmation" -m "Assisted-by: GitHub Copilot"

  • Check it: git log -1 shows the last commit with its full message.

When: taught in week 3; required on AI-assisted commits from week 11. Name the tool you used (Gemini, GitHub Copilot, Copilot CLI). One line per tool if you used more than one.

Why: it's how professionals disclose AI help. Open-source projects including LLVM, OpenStack, OpenTelemetry and Fedora use an Assisted-by: line, and about half of 281 open-source AI policies studied in 2026 require disclosure (All Things Open; Hora et al.). It also makes your own history searchable: git log --grep "Assisted-by".

The two-strikes rule ​

If two attempts to fix the same problem fail:

  1. Stop. Don't paste the error a third time.
  2. Go back to your last good commit if things got worse.
  3. Start a fresh chat (long, muddled conversations make the AI worse).
  4. Rewrite the prompt with what you learned: what you tried, the exact error, what you expected.

A Describe-step example ​

text
Goal: Add a "clear all" button to my to-do list.
Context: It's a single-page app in index.html, style.css and app.js. Items are saved in localStorage under the key "todos".
Constraints: Plain JavaScript, no libraries. Ask me to confirm before clearing. Don't change any other feature.
Done when: Clicking the button, then confirming, empties the list; reloading the page shows it's still empty; cancelling leaves the list unchanged.

A Plan-step example ​

text
Don't write any code yet. Propose a plan in 3–5 small steps for the goal above.
For each step, say which file changes and how I can check it worked.
