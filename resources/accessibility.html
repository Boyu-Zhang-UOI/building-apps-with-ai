Screen Reader and Keyboard Guide ​

How to use the course's tools with a screen reader or the keyboard alone, and how the course handles timed builds, read-aloud activities and video. Also useful if you use zoom, voice control or captions. If something in the course doesn't work with your setup, tell your instructor in week 1, or open an issue. It's a course problem, not yours.

On this page: Before you start · Chat assistants · GitHub · github.dev and Codespaces · DevTools · Timed builds, read-aloud activities and video · Accommodations · Your own pages

Before you start ​

  • Use the screen reader and browser you know. Every course tool runs in a web browser, so a current Chrome, Edge or Firefox works well with NVDA or JAWS on Windows, Safari or Chrome with VoiceOver on a Mac, and ChromeVox on a Chromebook.
  • Find commands by name, not by icon. When a step says "click the icon", you can almost always search for the command instead: the Command Palette in VS Code, ? on GitHub, the Command Menu in DevTools. Each is covered below.
  • Every course page is plain text. Slides are Markdown files (slides.md in each week) that you can read directly. Diagrams have text versions: the Safe Loop is a numbered list, and the trust boundary is a set of lists. AI-use labels always include words: 🟢 AI on, 🟡 AI limited, 🔴 AI off.
  • Shortcuts are given for Windows (which usually also work on Linux and ChromeOS) and Mac, with Linux listed separately where it differs. Menus and shortcuts move. If one doesn't work, search the tool's help for "keyboard shortcuts".

Chat assistants ​

You use a chat assistant most in weeks 1–6. Chat assistants change their interfaces often, so these are approaches rather than exact keys.

  • Wait for the reply to finish before reading it. Some screen readers announce a streaming reply in pieces. Then jump to the last reply by heading or by landmark. Code blocks usually have a Copy button right after them.

  • Live previews are hard to explore. The preview panel (Gemini's Canvas, Claude's Artifacts) runs your page inside a frame that some screen readers handle badly, and some previews don't let you type. Copy the code into a file and open it in its own browser tab instead, using the week 1 lab's No preview? Run it yourself. Or publish it on GitHub Pages and test the live page.

  • Ask the assistant for text descriptions. These prompts help:

    text
    Describe the page you just made, element by element, in reading order.
List every button, link and input box, with its visible label and its accessible name.
Check the page for accessibility problems: missing labels or alt text, low contrast, headings out of order, anything a keyboard can't reach. List them; don't fix anything yet.

  • Habit 2, "show, don't describe", doesn't need a drawing. A structured outline ("header with my name; three project cards in a row; a contact link at the bottom") or a link to a page you like counts as a reference.

  • If your chat tool doesn't work with your setup, switch to another one from the chat-assistant row of Tool Handout. The course prompts work unchanged.

GitHub on the web ​

  • Press ? on any GitHub page to hear or see its keyboard shortcuts.
  • Useful shortcuts: s or / to search, t to find a file in a repository, . to open the repository in github.dev, g then c for the Code tab, g then p for Pull requests.
  • Single-key shortcuts can clash with your screen reader's quick keys. GitHub lets you turn character-key shortcuts off in your account's accessibility settings. Menus move; search GitHub's docs for "keyboard shortcuts settings" if you can't find it.
  • Pull requests (weeks 12–14): in the Files changed tab, choose the unified (one-column) view, which reads more simply than split view. To get a whole pull request's diff as plain text, add .diff to the end of its address, as in https://github.com/[username]/[repo]/pull/1.diff.
  • Edit files in github.dev (press .) rather than in the web page's own editor: github.dev has all the VS Code features below.

Tips:

  • Screen reader mode is usually switched on automatically when VS Code detects a screen reader. If it isn't, run Toggle Screen Reader Accessibility Mode from the Command Palette. Accessibility Help in the editor tells you whether it's on.
  • In a browser, some shortcuts belong to the browser (such as closing or opening tabs). If a shortcut does the wrong thing, open the Command Palette and type the command's name instead.
  • Copilot Chat: open the Command Palette, type chat, and choose the command that opens the Chat view. After a reply arrives, open the Accessible View (Alt+F2 on Windows) to read it line by line and copy code.
  • Copilot's grey suggestions (completions) can be read with the Accessible View. If they get in your way, turn them off and use Chat only (how); that's the same setting AI-off activities use.
  • Sounds for errors and events: VS Code can play a sound for an error line, a warning, a finished task and more. Run Help: List Signal Sounds from the Command Palette to choose which.
  • Long terminal output (npm test, error logs): with the terminal focused, open the Accessible View to read it line by line. Or save it to a file and open that: npm test > test-output.txt 2>&1. Don't commit that file.
  • git's pager: git log and git diff open a scrolling viewer that some screen readers handle badly. Add --no-pager, as in git --no-pager log --oneline, to print the output straight into the terminal.
  • Prefer a desktop app? A Codespace can also be opened in the VS Code desktop app, which some screen-reader users find smoother; the Codespace still runs in the cloud. Look for the option to open it in VS Code Desktop (menus move).

  • Command Menu is the quickest way around: type "Console", "Network", "Application" or "Lighthouse" and press Enter.
  • Errors without DevTools: in the starters from week 9 on, server errors are written as plain text in the terminal where npm run dev runs. To see what your server returns, you can use curl in the terminal instead of the Network panel (how).
  • Check what your screen reader will announce: in Chrome or Edge, the Accessibility pane under Elements shows each element's role and accessible name, and the Lighthouse panel runs an accessibility audit that lists problems as text. Firefox has an Accessibility Inspector. Chrome's own DevTools documentation has a page on using DevTools with assistive technology.

Timed builds, read-aloud activities and video ​

These adjustments are open to everyone, with or without an accommodation letter.

Timed builds ​

The course's timed activities each fit inside one 75-minute studio: the Game in an Hour (week 3), the Debug Clinic (week 7), Be the Agent (week 11), the RLS Attack Lab (week 13) and the AI-off maintenance task (week 14). Timed parts are graded on effort and save points, not speed, and anyone may do them untimed (assessment). If you need extra time, tell your instructor in week 1, so it can be planned around that studio instead of cut from the activity. Pick a game from the game menu that suits your setup: turn-based games with keyboard controls and text output (a guessing game, a quiz, a typing test) are much easier to test with a screen reader than fast action games. Ask the AI to announce changes, such as the score, in a status message that screen readers read out (an aria-live region).

Read-aloud activities ​

  • Be the Agent (week 11) normally has the Model and the Harness talk aloud. You can run it entirely in typed messages instead, in a shared chat or document. The kit's task and tool cards are Markdown files you can zoom or read with a screen reader. Working alone, use the solo version.
  • Peer explanation swaps, pitches and debriefs: typed instead of spoken is fine. Ask for a quieter corner if the room is noisy.
  • Oral walkthroughs: extra time, a written-first version, typed answers, breaks, a quiet room and your own assistive technology are all available (walkthrough accommodations). The examiner can read code aloud if that helps.

Video ​

  • Your week 15 demo video needs captions or a transcript; writing your script first gives you the transcript. If recording or speaking is a barrier, a silent recording with captions or on-screen text, a sequence of screenshots with written narration, or a live 3-minute demo to your instructor all count the same (week 15 lab).
  • Record somewhere quiet. If the studio is noisy, record at home later.
  • Recorded concept talks are posted on Canvas. If one has no captions, ask. Each talk's slides.md is the same content in text.
  • Recording studios yourself is allowed with the instructor's consent or as an approved CDAR accommodation, and in either case you tell the instructor first (syllabus).

Asking for accommodations ​

If you believe you need disability-related academic adjustments, contact the University of Idaho's Center for Disability Access and Resources (CDAR). The full statement, address and phone number are in the syllabus.

  • Contact CDAR early, ideally before the course starts or in week 1. A current CDAR accommodation letter is needed for adjustments beyond those open to everyone, and adjustments are not retroactive.
  • Tell your instructor in week 1 what you use (a screen reader, captions, voice control, extra time) so demos, labs and walkthroughs can be set up for it. You don't have to say why.
  • Everything on this page is open to all students without a letter: untimed timed builds, typed answers, the video alternatives, the tool approaches above. The full list is in Assessment: Accommodations.

Following the course on your own? Use any of these adjustments freely; see the self-paced path.

Making your own pages accessible ​

The same skills make your own projects usable by everyone. Week 2 has an accessibility check of your home page, and week 15 has a full polish pass (polish checklist). The quick version:

  1. Keyboard test: put the mouse away and press Tab through the page. You should reach and use every button and field with Tab, Enter and Space, and always see where you are.
  2. Screen reader test: listen to the page from the top. Do the headings make an outline? Does every image have alt text, and every field a label?
  3. Audit: run DevTools' Lighthouse accessibility audit and fix what it lists, most serious first.
