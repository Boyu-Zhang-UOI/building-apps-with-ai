Week 6 — From Spec to App ​

Judge an app by your criteria, keep the code you can read, and write the check before the code.

Learning objectives ​

By the end of this week you can:

  1. Judge an app against written acceptance criteria instead of by how it looks.
  2. Find what an app builder generated behind its preview, read its usage dashboard, and say how you'd export your work to avoid lock-in.
  3. Keep a web app's rules in a module of pure functions, apart from the code that touches the page and storage.
  4. Write an automated test before the code it checks, and watch it go from red to green.
  5. Test each step in a Codespace preview before you commit it, and read the Console when the page goes blank.
  6. Publish a first version with an acceptance table that says honestly what passes.

Before class ​

  • ☐ Finish the week 5 homework: a revised SPEC.md, TESTS.md with a logic plan, and your first failing test.
  • ☐ Check your sign-in for the builder you were given. Under 18, or in the EEA, UK or Switzerland? Your instructor will tell you which builder to use.
  • ☐ Skim the bake-off scorecard.

Key ideas ​

Working on your own? Read this section, then do the lab; the self-paced path replaces the pair activities.

Judge by criteria, not vibes. The first builder that looks polished will feel like the winner. Your criteria are the scoreboard: test them in order, write what happened, count the MUSTs that pass. A beautiful app that fails AC3 fails AC3. When a criterion fails in two builders, suspect the spec first.

What's under the hood. Last week you heard that app builders generate a whole project. Now you look: a package.json listing libraries, files ending .tsx (usually React), a "build" script (a build step), maybe a database or login you didn't ask for. Could you debug it with the AI switched off?

Lock-in and credits. If a builder shuts down or changes its free tier, an app that lives only there goes with it. Some builders the course used to recommend have closed (Tool Handout), so anything you keep lives in GitHub. Builders run on credits: read the usage dashboard before and after. Students in CMU's AI coding course ran out mid-assignment (CMU 15-113).

The version you keep. Your Project 1 stays plain: index.html (structure), style.css (looks), app.js (behavior) and lib/ (the rules), with no framework and no build step. You can read every line, next week you debug it with the AI off, and GitHub Pages hosts it free.

Rules in their own module. app.js is the only file that touches the page (the DOM, through document) and storage. The rules from your logic plan live in lib/ as pure functions that a module shares with export; app.js loads them with import, and so does your test, which Node runs without a browser. In Python terms: functions you can import into a test, not logic tangled up with input() and print(). Anything that needs today's date takes it as an argument.

Check first, now with a test. From this week, where the logic allows it, the check you write before asking for code is an automated test: run it, see it fail (red), ask for the step, see it pass (green). That's red/green testing. The order matters: in a 2026 study, tests written after buggy code caught 14% of the faults, against 25% for tests written independently (Konstantinou et al.). Never let the AI change a test to make it pass. Where there's no rule to test (a layout, a button's label), the check is a manual test you write down first (check first).

Preview before you commit. In a Codespace, a small web server shows each change before anything is saved to GitHub. That's the Safe Loop's order: check first, one step, test (npm test and the preview), read and write a teach-back in PROMPTS.md, then commit. A blank page is information: open the Console and read the red line first.

Understanding check ​

The week 6 exit ticket is 🔴 AI off and graded on completion, not correctness. It opens with a look-back question about your week 4 work, answered from memory. Its central question: given a spec and what an app actually does, which acceptance criteria fail, and why? To check yourself first:

  • Name a criterion that failed in the bake-off, and say whether the builder or your spec was at fault.
  • Name one thing a builder generated that you didn't ask for, and why it matters.
  • Explain why the functions in lib/ must not use document or localStorage.
  • Show a test you watched fail before it passed, and say what the red proved.

Homework ​

Core (about 5 hours with project time): Project 1 version 1 live, passing at least half of your MUST criteria, with at least one automated test passing; a README with an acceptance table; TESTS.md; PROMPTS.md; your scorecard. On Canvas: the bake-off Verdict, this week's reflection. Details: homework. The final version is due before week 9 Studio A, with at least three automated tests of its pure logic, graded with the Project 1 rubric and oral walkthrough 1 in week 8.

If a tool is down ​

If this failsDo this
Google AI Studio (down, age-restricted, or out of quota)Use Bolt as builder A, and Lovable or v0 as builder B (Tool Handout)
Every builder is unavailableRun the bake-off with two chat assistants instead (for example Gemini Canvas and ChatGPT), with the same prompt and scorecard
Your chat assistantSwitch to a fallback in the Tool Handout and paste your SPEC.md into a fresh chat
Codespaces won't start, or you're out of hoursEdit in github.dev (press . on your repository page) and test on GitHub Pages after each commit. It has no terminal, so npm test waits (troubleshooting)
GitHub Pages is slow to updateWait up to 10 minutes and check the Actions tab. Keep testing in your Codespace preview meanwhile
Out of credits anywhereI ran out of free credits
