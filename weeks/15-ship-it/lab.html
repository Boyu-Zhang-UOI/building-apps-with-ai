Week 15 lab — Polish, secure, record, rehearse ​

Two studios. Studio A: a polish sprint on your capstone: the empty, loading and error states, phone width, title and favicon, and accessibility, including one fix you write by hand. Studio B: an honest Known issues section, a final security pass, a 2–3 minute demo video and a rehearsal of your Project Fair pitch. Do the Core parts first. If time parts are optional. Work in the Safe Loop: check first, small step, test, read the diff, teach back, commit.

AI-use key: 🟢 AI on: use AI freely, in the Safe Loop · 🟡 AI limited: the AI may explain and critique, but you decide and write · 🔴 AI off: no AI tools at all, including code completions.

What you need: your deployed capstone and its production URL, the Polish checklist, the Project Fair guide (for the feedback card) and a free built-in screen recorder (Part B3).

NOTE

No exit ticket and no oral walkthrough this week. University Regulation H-1-a doesn't allow quizzes or exams in class during the week before finals. Both studios are build time.

Part A1 — Set up the sprint (Core, 5 min) ​

🟢 AI on for fixes, except the one in Part A2 that you write yourself. Work through the Polish checklist against your live site. Fix the quick wins first. You won't finish every item: that's expected; the rest is homework.

  1. Open your production URL (not localhost) in a normal window, and again at phone width with your browser's device toolbar. The device toolbar is part of DevTools, the browser's built-in developer tools (F12, or Cmd-Option-I on a Mac).

  2. Work in this order: the three states (empty, loading, error) → phone → title and favicon → accessibility. The README and its Known issues section come in Studio B.

  3. For each fix, write the "done when" check first. Where the fix is pure logic (choosing an empty-state message, formatting a date), the check is an automated test you write before the code and run with npm test. For layout, focus and wording, the check is a manual step you write in TESTS.md. Then prompt in the Safe Loop, for example:

    text
    Goal: While my saved notes load, show "Loading your notes…" and disable the Save button; if loading fails, show "Couldn't load your notes. Check your connection and reload."
Context: public/app.js loads notes with fetch('/api/notes') in loadNotes() and writes them into <ul id="notes">. The starter's "Ask the AI" form in the same file already shows a message, disables its button, and uses try/catch/finally.
Constraints: Only change loadNotes() and style.css. Use textContent, not innerHTML. Don't change the server route.
Done when: With the network throttled I see the loading line; with the network offline I see the error line and the Save button works again; a normal load looks the same as before; npm test passes.

    Test every case yourself, read the diff (only the function you named should change), write a short teach-back in PROMPTS.md, and commit with an Assisted-by: line.

Part A2 — The three states, phone, title and favicon (Core, 20 min) ​

Trigger each state on purpose. Each should look intentional, with words that say what to do next.

  • Empty: open the app with no data. Sign in as a fresh test user, or delete your app's saved data (DevTools → Application → Local storage). Menus move: ask your assistant where it is in your browser.
  • Loading: throttle the network (DevTools → Network, choose a slow preset) and reload.
  • Error: set the same menu to Offline, or submit bad input.

Write the empty-state fix yourself (🔴 AI off, including completions). It's a small, real code change: find where the list is drawn, add a condition for "no items", and show a helpful line such as "No notes yet — add one above" instead of a blank space. Check first: if the message comes from a pure function in public/lib/ (like the starter's summarize(items) in public/lib/items.js), add a test for the empty case before you change it; otherwise write the manual check in TESTS.md. Commit it without an Assisted-by: line, and note it under "What I wrote or decided myself" in PROMPTS.md.

TIP

A Python habit to drop. In Python, if not items: is true for an empty list. In JavaScript an empty array [] is truthy, so if (!items) is false and the empty state never shows. Test items.length === 0 instead (and use ===: JavaScript's == converts types first, so 0 == '' is true).

Loading and error (🟢 AI on). Use a prompt like the one in Part A1. JavaScript's try/catch/finally works like Python's try/except/finally: put the line that hides "Loading…" or re-enables the button in finally, so it runs whether the request worked or failed.

Phone. At phone width nothing scrolls sideways, buttons are big enough to tap, and text is readable without zooming. If the page looks zoomed out on a real phone, check index.html has the viewport tag from section 2 of the Polish checklist.

Title and favicon. The browser tab should name your app: the starter's says "My Capstone" until you change the <title> in index.html. Add a favicon, the small icon in the tab: even a simple SVG works, with <link rel="icon" href="favicon.svg"> in the <head>.

✅ Checkpoint: you triggered all three states and each looks intentional, the app works at phone width, the tab shows a real title and a favicon, and your hand-written empty-state fix is committed. Check each one on the production URL after the deploy finishes.

Part A3 — Accessibility and the keyboard test (Core, 15 min) ​

🟢 AI on for finding problems and fixes. Two of the most common misses, and their fixes:

  • An image with no alt: add alt="Chart of weekly totals", or alt="" if it's purely decorative.
  • An input with no label: wrap it, for example <label>Name <input id="name"></label>, or add aria-label="Name".

The keyboard test (do this one live). Put your mouse away. Press Tab through your whole app. You should be able to reach and use every button and field with Tab, Enter and Space, and always see where you are (a focus outline). If focus disappears, look in your CSS for outline: none and give focused elements a visible style instead, for example :focus-visible { outline: 3px solid #1d4ed8; }.

Then check that nothing important is shown by color alone (an error that only turns a box red): add words or an icon too.

TIP

Not sure about color contrast or missing labels? Your browser's built-in accessibility panel, or its Lighthouse audit, flags both. Menus move: ask your assistant where it is in your browser. If you use a screen reader yourself, the Accessibility guide covers the course's tools.

✅ Checkpoint: you tabbed through the entire app with no mouse and could see and use everything; every meaningful image has alt text and every input has a label. Commit after each fix.

TIP

A fix broke another feature? You have a save point: git restore [file], or revert the commit, and try a smaller step (the two-strikes rule). The live site looks different from localhost? The production URL is the one that's graded: push, wait for the deploy, and re-check. A hard reload (Shift-reload) rules out an old cached copy.

Part A4 — Content and copy (If time, 10 min) ​

Section 5 of the Polish checklist: no leftover placeholder text ("Lorem ipsum", "TODO"), buttons that say what they do ("Save note", not "Submit"), numbers and dates formatted for a person, and spelling checked. Formatting is pure logic, so write the test first, for example that your formatter turns 1234.5 into $1,234.50. JavaScript's Intl.NumberFormat and toLocaleDateString() do most of the work. Dates have a trap that a test catches: new Date('2026-12-14') means midnight UTC, which is still December 13 in Idaho.

Checkpoint share (5 min): two or three people say one thing the keyboard test or the three states showed them, and what they changed.

Part B1 — README with an honest Known issues section (Core, 15 min) ​

🟡 AI limited: you decide what's true; the AI may critique your wording. Open your README (from the README template) and fill in Known issues. For each issue: what doesn't work, when it happens, any workaround, and what you'd do next. For example:

markdown
## Known issues

| Issue | When it happens | Workaround or plan |
|---|---|---|
| Long notes overflow the card | Notes over about 300 characters, at phone width | Turn the phone sideways. Plan: let the text wrap in `.card` (style.css) |
| Everyone shares one list | Always: there's no sign-in in v1.0 (out of scope in SPEC.md) | Plan: Supabase Auth with per-user policies |
| The weather panel says "unavailable" | When the public weather API is down | Reload to retry |

Use what you found in Studio A: the states you couldn't fix in time, the phone layout that still wraps oddly, the label you haven't added yet. Then put the bigger ideas under Next steps.

Naming a real limitation never costs points, and the Project Fair gives credit for it. Hiding one that a grader finds does.

✅ Checkpoint: your README lists at least one honest known issue, with when it happens and what you'd do next, and it's committed. The rest of the README (section 6 of the Polish checklist) is homework.

Part B2 — Final security pass (Core, 15 min) ​

🟢 AI on for explaining results. Re-run the week 14 checks so nothing regressed while you polished.

bash
npm test
npm run check:secrets
npm audit
grep -rn "innerHTML" public/

npm run check:secrets scans your files and your whole git history, so a clean result covers old commits too. Then, on the live site:

  • Open DevTools → Sources and Network. Confirm no secret key is visible (only the project URL and publishable key, if you use Supabase).
  • Type <img src=x onerror=alert(1)> into every input, and reload if the app saves it. No alert should appear. If one does, that's XSS: find the innerHTML and switch to textContent.
  • If you have a database: Database → Advisors → Security shows no "RLS Disabled" error, and the check query at the end of supabase/policies.sql still matches your "who may do what" table from week 13.
  • In Vercel's project settings, confirm every secret is an environment variable there, and none is in your code.

Update SECURITY_CHECKLIST.md template with fresh evidence and today's date.

WARNING

If a key turns up in your code, your history or the browser, fix that before you record anything. Revoke the key and make a new one first, then clean up (Troubleshooting: I committed a secret).

✅ Checkpoint: tests pass, no secrets found (including in history), the XSS payload stays inert, and RLS (if any) is on with the grants you intended.

Mini-lesson (5 min): your instructor goes back to the story slide (problem → demo → how → what broke → what you learned) and records a short demo live with the built-in recorder, then shows how to add captions.

Part B3 — Record your demo video (Core, 25 min) ​

A 2–3 minute video so people can see your app even when it isn't running. Find a quiet corner if you'll speak.

Free built-in recorders:

  • macOS: press Shift-Cmd-5, choose to record the whole screen or a selected portion, then Record. Stop from the menu bar.
  • Windows: Snipping Tool (it records video), or the Game Bar (Win-G, then record).
  • ChromeOS: the Screen capture tool in quick settings, set to video.
  • Any device: a phone camera pointed at the screen is acceptable for grading.

What to record (the story shape):

  1. Problem (about 15 seconds): who it's for and what it solves.
  2. Demo (60–90 seconds): do the main task live, including your feature types and one edge case handled well (empty input, an error).
  3. How (about 20 seconds): one line on how it's built and where the data and secrets live.
  4. What broke and what you learned (about 20 seconds): one honest moment.

Make it accessible. Add captions (automatic captions are fine once you've fixed their mistakes) or a transcript. Writing your script first gives you the transcript for free. Put the transcript in your README under the video link, or upload it with the video.

Can't record, or can't speak on a recording? Any of these counts the same: a silent recording with captions or on-screen text; a short sequence of screenshots with written narration; or a live 3-minute demo to your instructor, who notes it on Canvas. Ask early; the Accessibility guide explains how the course handles video.

Privacy:

  • Close .env, terminals and dashboards before you start. Never show API keys, your Vercel or Supabase dashboards, or real people's information. Use made-up data.
  • Upload it as an unlisted video (only people with the link can watch) and put the link in your README and your Canvas submission. Rather not have your voice or face reachable from a public repo? Upload it to Canvas only and write "Demo video: submitted on Canvas" in the README.

Tips: rehearse once before you hit record; one clean take beats ten edited ones. If you fluff a line, keep going. Check the file plays and is under 3 minutes before you upload.

✅ Checkpoint: a 2–3 minute video exists, plays and shows no secrets. Captions or a transcript, the upload and the README link can be finished in the homework.

Part B4 — Rehearse your Fair pitch (Core, 10 min) ​

Pair up. Each of you gives your 60–90 second Fair pitch (problem → quick demo → one thing you're proud of → one known issue) and hands your partner the app at its production URL. Your partner tries it, fills in a feedback card (🔴 AI off), and says one thing that landed and one thing to tighten. Swap.

Working alone? Record your pitch, watch it back, and fill in the feedback card yourself (Self-paced path).

✅ Checkpoint: you've said your pitch out loud once and have one concrete note to apply before the Fair.

Part B5 — Final-submission check (If time, 5 min) ​

Open the final submission checklist on the week 16 page. Tick what's already done, and write down the one or two things that are left and when you'll do them. This is your plan, not a quiz: nobody collects it.

Wrap up ​

  • Commit all polish changes, the Known issues section and the updated SECURITY_CHECKLIST.md.
  • Make sure your README has the production URL, a screenshot and the demo video link (or "submitted on Canvas").
  • Finish the rest of the Polish checklist and the homework before the Project Fair.
  • The Fair is in finals week, in the course's scheduled final exam slot (the day, time and room are on Canvas). Open your Supabase project the day before so it isn't paused.
  • Missed walkthrough 3 in week 14 for illness or another recognized reason? Tell your instructor: it's rescheduled without penalty, outside this week's studios (what to expect).
