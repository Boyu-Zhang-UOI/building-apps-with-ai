Week 11 — How Agents Work ​

An agent is an LLM in a loop with tools. You decide what it may do; your tests decide whether it worked.

Learning objectives ​

By the end of this week you can:

  1. Describe an agent as a model, tools, a loop and a context window (its working memory), and trace what it does one tool call at a time.
  2. Ask an agent to plan first, keep approvals on, and run it inside a sandbox with save points before and after.
  3. Write a short AGENTS.md with a Scope section, and explain why it's advice, not enforcement.
  4. Recognize how agents fail (fake success, deleted data, publishing what should stay private), using real incidents.
  5. Build a feature with an agent: the test first, in a separate prompt; red then green in your own terminal; a teach-back before the commit.

Before class ​

  • ☐ Your capstone pitch is submitted and you've read your instructor's reply (Go, Shrink or Rethink). This week it becomes your SPEC.md.
  • ☐ Your capstone repository exists, created from the starter as part of the pitch milestone, and npm test passes in its Codespace (how). Pairs: one partner creates it and adds the other as a collaborator.
  • ☐ Copilot Chat's mode picker offers Agent. Check your credits (the Copilot icon in the status bar): agent work uses them much faster than chat.

WARNING

From this week, an AI can edit your files and run commands. Re-read rules 3, 4, 7 and 9 of the Safety Contract. Approvals stay on all week; autopilot and skip-permissions modes are never allowed in this course.

Key ideas ​

If you are working through this week on your own, read this section, then do the lab.

An agent is an LLM in a loop with tools ​

An agent has tools (list files, read, search, edit, run a command) and works in a loop: it chooses a tool call, the harness (the program around the model) runs it, the result goes back into its context, and it chooses the next step, until it believes the task is done. Everything it knows comes from that context: your prompt, standing instructions and every tool result so far. It never sees your screen. In Be the Agent you play both halves of the loop by hand.

Context is working memory ​

Everything the agent reads fills its context window, and as it fills, details get squeezed out. So: one task per session, and short standing instructions.

Plan first, approvals on, inside a sandbox ​

Ask for a plan before any code ("Plan first and wait for my approval"), or pick Plan where your tool has it, and edit the plan before you approve it. Agents ask before running commands; you can switch that off. Don't. Allow each command once, after reading it. Run agents in a sandbox, where mistakes can't reach anything you care about: your Codespace holds one project and no personal files. Commit before and after every agent task, and push: an agent's own undo is not a backup.

How agents fail ​

In 2026, an agent on a routine test task used a key it found in an unrelated file to delete a company's production storage, and its backups, in about nine seconds (case 13); and agents asked to attach screenshots to code reviews put 13,000+ internal screenshots in public repositories, with no attacker involved (case 14). Earlier agents deleted a production database and faked the results, or overwrote and wiped a user's files (cases 4, 5 and 6).

AGENTS.md is advice, not enforcement ​

AGENTS.md is "a README for agents" (agents.md): what the project is, the commands, what the agent may change (Scope), and what it must never do. Keep it short, and read any rules file from the internet before you use it. A scope sentence measurably helps: removing only the scope and consent statement raised one agent's out-of-scope actions from 0% to 17.1% in 7,500 runs (Qu et al.). But the agent reads the file; nothing makes it obey ("context, not enforced configuration", say Anthropic's docs). What actually protects you is outside the agent's control: the Codespace, the approval prompts you answer, scoped keys that can do only one job (or none within reach), spending caps on paid accounts and, from week 13, database rules.

Check first, then teach back ​

An agent can't see your app; a test is how it, and you, check the work. Write the test before the code, in a separate prompt: AI-written tests that come after faulty code tend to agree with it, catching 14% of faults against 25% for tests written independently (Konstantinou et al.). Watch it fail (red), then pass (green), in your own terminal. Before you commit, write a 2–3 sentence teach-back in PROMPTS.md (how), and end the commit message with an Assisted-by: line, required from this week (how).

Credits are a budget ​

Agent sessions make many model calls. On Copilot's free plans, when the credits run out, agent work stops until the monthly reset (Tool Handout). Small, clear tasks cost less.

Understanding check ​

  • The week 11 exit ticket (🔴 AI off) at the end of Studio B, including one question about a decision in your week 9 micro-app. Graded on completion, not correctness.
  • No walkthrough this week, but oral walkthrough 2 in week 12 asks you to explain the feature you build in Studio B, with the AI off (what to expect). Only commit code you can explain.

Homework ​

About 5 hours, including project time. Details and the checklist are in Week 11 Homework — Finish the first feature, complete the spec, deploy.

  • Core: finish your first feature and publish its branch; trace your agent's run (🔴 AI off); complete SPEC.md; deploy the capstone; PROMPTS.md with teach-backs; reflection on Canvas.
  • Stretch: read a minimal agent loop; try the Copilot CLI.

Scored with the weekly rubric; the capstone has its own rubric.
