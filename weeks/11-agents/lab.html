Week 11 Lab — Be the Agent, then direct one ​

Two studios. In Studio A you play an agent by hand, then open your capstone and give it an AGENTS.md with a Scope section. In Studio B you build the capstone's first feature with a real agent: the test first, in its own chat, then plan, build, check and teach back.

AI-use key: 🟢 AI on: use AI, following the Safe Loop · 🟡 AI limited: only in the way the step says · 🔴 AI off: close AI chat and turn off completions.

This week's rules for agents: approvals stay on (never autopilot or skip-permissions modes); commit before and after every agent task; read every command before you allow it; the agent never gets your keys. Stuck at any point? See Troubleshooting at the bottom of this page.

Only commit code you can explain. In week 12 the feature you build in Studio B becomes your first pull request: you read its whole diff, and a classmate plants a bug in it for you to find with the AI off.

Before Studio A: create your capstone repository ​

About 15 minutes, before class (it's part of the pitch milestone):

  1. Create your capstone repository from the starter by following Start a project from a starter, with the vc101-capstone-starter template. Give it your project's name, make it public, and keep it in your personal account (so Vercel can deploy it). Pairs: one person creates it and adds the other as a collaborator (Settings → Collaborators).

  2. Open it in a Codespace and run the tests:

    bash
    npm test

  3. Check that Copilot Chat's mode picker offers Agent, and look at your credit usage (the Copilot icon in the status bar).

  4. Stop the Codespace (github.com/codespaces → ⋯ → Stop codespace).

✅ Checkpoint: npm test ends with fail 0, and your repository is on github.com under your own username.

Part A1 — Be the Agent (30 min) ​

Core · 🔴 AI off (unless you choose the "Working alone?" option with an AI as the Model)

Why: an agent only knows what its tools return. Playing both halves of the loop shows you what an agent needs, and where it goes wrong.

Work in pairs. One of you is the Model, the other is the Harness (the program that runs the model's tool calls). Everything you need is in the kit: the Be the Agent README (roles and rules), the tool cards (the five tools and their exact commands) and the task cards (the bug report and a call log).

NOTE

The kit contains a planted bug on purpose. One test fails until you fix it.

  1. Setup (Harness, 3 min). Create a repository from the kit by following Start a project from a starter, with the vc101-be-the-agent template, and open it in a Codespace. Open a terminal, close all editor tabs and collapse the Explorer. Don't run anything yet.

  2. Task A (20 min). The Model reads Task A on the task card and writes one tool call at a time, for example:

    text
    CALL 1: run

    The Harness types the matching command from the tool card, for example:

    bash
    npm test

    and reads the output aloud, word for word (or shares the screen, if reading aloud doesn't suit you). The Model logs each call and what it learned. Keep going until the Model writes a Finish report with test output as evidence.

  3. Fast pairs: swap roles and do Task B, the feature request, red then green.

  4. Rules to remember: the Model never looks at the editor; the Harness never hints or fixes the Model's typos; nobody edits the tests to make them pass.

TIP

Working alone? Choose one:

  • With your instructor (🔴 AI off). In a small class, your instructor plays the Model and you play the Harness for Task A; then swap for Task B.
  • Play both roles (🔴 AI off). Keep the editor closed. Before each call, write it in the call log and say what you expect it to show; then run it and write what you actually learned. You may only use what the terminal has printed.
  • An AI plays the Model (🟢 AI on). This is the one time an AI may work on the kit, and only through tool calls that you run. Open a fresh chat with any chat assistant. Paste the kit's "Roles" and "Rules" sections, the whole tool card page and Task A, then say: "You are the Model. Write exactly one tool call at a time, then wait for me to paste its output." You are the Harness: run each call exactly as written, typos included, and paste back the full output. Don't hint. Afterwards, answer the debrief questions about the AI's calls.

✅ Checkpoint: the Harness runs npm test one last time and it ends with fail 0. The Model's call log shows every call, and the Finish report quotes the test summary.

Debrief (last 7 minutes) ​

Discuss in your pair, then share one answer with the class:

  1. What context did the Model need before it could fix anything? Which single call told you the most?
  2. How many tool calls did you make? Which were wasted?
  3. Did an edit fail? What did that teach you about how agents must quote code?
  4. How did you know you were done? What if you'd skipped the last run?
  5. What would have helped? Write the three-line AGENTS.md you wish the kit had.

Afterwards, the Harness can commit the fix with a message that says what changed and why. Keep your call log: the homework compares it with a real agent's run. You won't use this repository again; stop its Codespace.

Part A2 — Open your capstone and give it an AGENTS.md (20 min) ​

Core · 🟡 AI limited: you write the file; Copilot in Ask mode may critique it

Why: an agent works best with good standing context. SPEC.md says what to build; AGENTS.md says how to work here, and what is out of bounds.

Open and check (5 min) ​

Open the capstone repository you created before class in a Codespace and check the shell works:

bash
npm test
npm run dev

Open the forwarded port 3000. The list example works straight away; the "ask the AI" example needs a key, exactly as in your week 9 micro-app (optional today). Stop the server with Ctrl+C.

Didn't create the repository before class? Do the four steps above now (about 10 minutes), and write a shorter AGENTS.md today: the Project line and the Scope section are what matter.

Write the Scope section (10 min) ​

The starter's AGENTS.md already describes the layout and the safety rules. Make it yours, keeping it short:

  1. Replace the Project line with one sentence about your app.
  2. Find the Scope section (if your copy has none, copy it from the AGENTS.md template). List only the folders an agent may edit for your project, for example public/, tests/, and api/ and lib/ only if you'll have a server route. Keep the sentence "Anything not listed here is out of scope", and the lines about asking before deleting, installing, publishing or making network requests, and never creating repositories, gists, releases or deployments.
  3. Add at most two conventions that matter for your project (for example "All dates are shown as YYYY-MM-DD" or "Keep the page usable on a phone").
  4. Read the whole file once, line by line. You're responsible for every instruction an agent follows.

IMPORTANT

AGENTS.md is advice, not enforcement. An agent usually follows it, but nothing stops it from ignoring a line. What actually holds: the Codespace (it can only reach this project), the approval prompts you answer, no keys within its reach (keep .env closed and out of the chat; any key you use does only one job), spending caps on paid accounts, and save points pushed to GitHub, which it can't delete without a command you'd have to approve. Week 13 adds database rules.

In VS Code, check two settings (Ctrl+,, Mac Cmd+,; names move, so search):

  • Search AGENTS.md: Use AGENTS.md file is ticked, so Copilot reads your file.
  • Search auto approve: nothing that approves all tools or all commands automatically is switched on. VS Code warns you before turning such a setting on; in this course, the answer is always no.

Commit (5 min) ​

Source Control → message Start capstone: AGENTS.md with scope → Commit → Sync Changes. (If Copilot critiqued your file, add an Assisted-by: GitHub Copilot line.)

✅ Checkpoint: on github.com, your repository shows your AGENTS.md with a Scope section, and the Actions tab shows a green check from the test workflow.

Part A3 — Your first criterion in SPEC.md (10 min) ​

Core · 🟡 AI limited: you write it; Copilot in Ask mode may critique it · due before Studio B

Why: Studio B's feature is built from one acceptance criterion, and the agent reads it from SPEC.md. The rest of the spec is homework.

  1. Open SPEC.md. Fill in sections 1 (Problem) and 2 (User) from your pitch: a few sentences each.

  2. In section 4, replace the example criteria with one acceptance criterion for your first feature, in WHEN … THE APP SHALL … form, plus one edge case of it. Pick a MUST criterion whose logic fits in a small, testable function in public/lib/. Good first features: "reject an empty or duplicate entry", "calculate the total, streak or average", "sort items by date", "format a date for display". Avoid anything that needs a database or a new API today.

    text
    AC1 | WHEN I add a habit with an empty or duplicate name, THE APP SHALL not add it and SHALL show "Please enter a new habit name". | MUST

  3. Optional (🟡 AI limited): ask Copilot in Ask mode, "Is AC1 in SPEC.md specific enough to write a test for? List at most 3 problems. Don't rewrite it." Decide yourself what to change.

  4. Commit and sync: SPEC: problem, user and AC1.

✅ Checkpoint: SPEC.md on github.com shows AC1 and its edge case, and you could say in one sentence what a test for it would check.

Wrap up Studio A ​

  • ☐ Be the Agent: debrief answers and call log kept; the kit's Codespace stopped.
  • ☐ Capstone AGENTS.md (with Scope) committed on main.
  • ☐ AC1 in SPEC.md, now or before Studio B.
  • ☐ Stop your Codespace to save your free hours.

The live demo: one small agent task, test first ​

Your instructor builds one tiny feature with Copilot agent mode. Watch for five things: the test is written first, in its own chat; the agent plans and waits; every command needs an approval click; the instructor runs npm test themselves; and a teach-back goes into PROMPTS.md before the commit. You'll do exactly this in Part B1.

Part B1 — Your first agent-built feature (50 min) ​

Core · 🟢 AI on: Copilot agent mode, approvals on · 🔴 AI off for the teach-back

Why: this is the Safe Loop with an agent doing the typing. Your job is what the agent can't do: choosing the task, writing the check, approving the plan, checking the evidence and reading the diff.

No AC1 yet? Do Part A3 first (10 minutes), and take the time from step 5.

1. Save point and a branch (3 min) ​

In the terminal:

bash
git status
git switch -c feature/ac1

git status should say "nothing to commit, working tree clean": that's your "before" save point. (If it isn't clean, commit first.) The second command starts a branch, a separate line of work: if this feature goes wrong, main, the version you'll deploy, is untouched. Week 12 teaches the rest of the branch story, and merges this one through a pull request.

2. Check first: the test, in its own chat (10 min) ​

The test comes before the code, and from a separate prompt that never sees the code, so it checks what your spec says rather than what the code happens to do.

Open Copilot Chat, start a new chat session, choose Agent in the mode picker, and adapt this prompt:

text
Goal: Write ONE test file for AC1 in SPEC.md, before the feature exists.
Context: Read AGENTS.md and SPEC.md. The logic will be a function addHabit(habits, name) in public/lib/habits.js that returns { habits, error }. Tests are tests/*.test.js and run with npm test (Node's built-in test runner; see tests/items.test.js for the style).
Constraints: Create only tests/habits.test.js. Do not create or change any other file, and do not write the function. Cover the normal case and the edge case in AC1.
Done when: the test file exists, you have run npm test, and you have pasted the output showing the new tests failing.

When Copilot asks to run a command, read the command before you allow it. Allow npm test once.

Then check the red step yourself, in your own terminal:

bash
npm test

The new tests should fail because the feature doesn't exist yet: an error such as "does not provide an export named …" or "Cannot find module", or a failed assertion. They should not fail because of a typo in the test. Read the test file: does it check what AC1 says? (Python readers: assert.equal(a, b) is like assert a == b, and assert.deepEqual compares lists and dictionaries, which JavaScript calls arrays and objects.) Then commit the failing test, so you'll be able to see if anything changes it later:

bash
git add tests/
git commit -m "Add failing test for AC1" -m "Assisted-by: GitHub Copilot (agent mode)"

✅ Checkpoint: you've seen the new test fail, for the right reason, in your own terminal, and it's committed.

3. Plan first, then build, in a new chat (14 min) ​

Start another new chat session (Agent mode, or Plan if your picker offers it). Adapt this prompt:

text
Goal: Make the failing tests in tests/habits.test.js pass by implementing AC1 from SPEC.md.
Context: Read AGENTS.md and SPEC.md first. Pure logic goes in public/lib/ and is wired into the page in public/app.js.
Constraints: Plan first and wait for my approval before editing anything. Do not change any file in tests/. This one criterion only. No new dependencies. Stay inside the Scope in AGENTS.md. Don't touch .env or api/.
Done when: npm test passes, you have pasted the output, and I can see the message in the browser when I try an empty or duplicate name.

Read the plan like a manager. Is it the right criterion? Does it touch only the files you expect? Does it leave tests/ alone? Reply with your edits ("Skip step 4", "Put the function in public/lib/habits.js"), then approve.

WARNING

Keep the default approval setting, where the agent asks before running commands, and allow each command once. If the agent proposes rm -rf, git reset --hard, git push --force, installing a package, or deleting or changing a test, click Skip and ask it why. If it reads a web page or someone else's file and then wants to do something you didn't ask for, stop the session (Safety Contract, rule 9).

4. Green, in your own terminal (3 min) ​

When the agent says it's done, don't take its word for it:

bash
npm test
git status --short

Every test should pass (fail 0). The second command lists every file changed or added since your test commit (M means modified, ?? means new): nothing in tests/ should be on the list. If the agent changed or added a test, it may have made the tests agree with the code instead of the spec. Discard that change (right-click the file in Source Control → Discard Changes) and ask the agent to fix the code instead.

✅ Checkpoint: fail 0, and no file in tests/ changed after your test commit.

5. Read it and try it (10 min) ​

  1. Read the diff. Open Source Control and click each changed file. For every line, ask yourself: can I explain this? For anything you can't, ask Copilot in Ask mode: "Explain lines 12–20 of public/lib/habits.js in plain English." Remove or simplify anything you don't need.
  2. Try it by hand. Run npm run dev, open the page, and test the normal case and the edge cases from your criterion. Reload the page. Try it on a narrow window.

6. Teach back (5 min) ​

🔴 AI off. In PROMPTS.md, add an entry for this agent task: the two prompts, the plan and what you changed in it, the red and green test output, and what you checked or fixed yourself. Then write the teach-back: 2–3 sentences, in your own words, on what changed and why it works (example). If you can't write it, read the diff again or ask Ask mode to explain it, then write it yourself.

7. Commit and push (5 min) ​

Commit everything with a clear message and the Assisted-by: line:

bash
git add -A
git status
git commit -m "Reject empty and duplicate habit names (AC1)" -m "Assisted-by: GitHub Copilot (agent mode)"

Read the git status list before you commit: no .env, nothing you didn't expect. Then publish the branch to GitHub: Source Control → Publish Branch (or git push -u origin feature/ac1). Don't merge it yet; that's week 12 Studio A.

✅ Checkpoint: git log --oneline shows your test commit and your feature commit on feature/ac1; the branch is on GitHub; PROMPTS.md has your entry with red and green evidence and a teach-back. Not there yet? Finish it as homework task 1.

Part B2 — Try the Copilot CLI (10 min) ​

If time · 🟢 AI on, approvals on

The same agent loop runs in the terminal. Try it on a tiny task on your feature branch, for example "add a test for the edge case I forgot":

  1. Commit first. Then start it:

    bash
    copilot

    If the command isn't found, install it with npm install -g @github/copilot (check the Tool Handout and the GitHub Docs first; installing runs code). If it asks you to log in, type /login and follow the steps. Don't start it with any option that allows all tools.

  2. It asks whether you trust the files in this folder: yes, it's your own capstone Codespace, cloned from GitHub.

  3. Press Shift+Tab to switch to plan mode, then paste a four-part prompt.

  4. When it asks to run a tool, choose "yes" once. Don't approve a tool "for the rest of the session".

  5. Check with npm test yourself, read the diff, write a teach-back, commit with Assisted-by: GitHub Copilot CLI.

Note in PROMPTS.md how the CLI compared with agent mode in the editor.

Part B3 — Read a minimal agent loop (15 min) ​

If time, for confident programmers · 🔴 AI off · read only: don't run it

Why: in Be the Agent, your partner was the harness. Here is a whole one in about 50 lines of JavaScript: a model, five tools, an approval check and a loop. askModel isn't shown; it sends the messages to an LLM API, much like your week 9 micro-app's server, and turns the reply into one tool call. Real agents add much more care, but the shape is the same.

js
// mini-agent.mjs: a minimal coding agent, for reading. Usage: node mini-agent.mjs "[task]"
import { readFile, writeFile, readdir } from 'node:fs/promises';
import { execFile } from 'node:child_process';
import { promisify } from 'node:util';
import { createInterface } from 'node:readline/promises';
import { askModel } from './lib/model.js'; // not shown: sends the messages to an LLM API

const exec = promisify(execFile);
const terminal = createInterface({ input: process.stdin, output: process.stdout });

const tools = {
  list_files: async ({ dir = '.' }) => (await readdir(dir, { recursive: true })).join('\n'),
  read_file: async ({ path }) => readFile(path, 'utf8'),
  search: async ({ text }) => {
    const found = await exec('grep', ['-rn', '--exclude-dir=node_modules', text, '.']).catch((err) => err);
    return found.stdout || 'No matches.';
  },
  edit: async ({ path, oldText, newText }) => {
    const code = await readFile(path, 'utf8');
    if (code.split(oldText).length !== 2) return 'Error: the old text must appear exactly once.';
    await writeFile(path, code.replace(oldText, () => newText));
    return `Edited ${path}.`;
  },
  run: async ({ command }) => {
    const done = await exec('bash', ['-c', command]).catch((err) => err); // a failing command still has output
    return `${done.stdout}${done.stderr}`;
  },
};

async function allowed(call) {
  if (['list_files', 'read_file', 'search'].includes(call.tool)) return true;
  const answer = await terminal.question(`Allow ${call.tool} ${JSON.stringify(call.args)}? (y/n) `);
  return answer.trim().toLowerCase() === 'y';
}

const messages = [
  { role: 'system', content: `Reply with one tool call as JSON.\n${await readFile('AGENTS.md', 'utf8')}` },
  { role: 'user', content: process.argv[2] },
];

for (let step = 1; step <= 25; step++) {
  const call = await askModel(messages, [...Object.keys(tools), 'finish']); // e.g. { tool: 'run', args: { command: 'npm test' } }
  if (call.tool === 'finish') {
    console.log(call.args.report);
    break;
  }
  let result;
  if (!Object.hasOwn(tools, call.tool)) result = `Error: there is no tool called ${call.tool}.`;
  else if (await allowed(call)) result = await tools[call.tool](call.args);
  else result = 'The user did not allow this call. Ask why, or try something else.';
  console.log(`[${step}] ${call.tool}: ${result.slice(0, 300)}`);
  messages.push({ role: 'assistant', content: JSON.stringify(call) });
  messages.push({ role: 'user', content: `Result of ${call.tool}:\n${result}` });
}
terminal.close();

Python readers: async/await work as in Python's asyncio: await waits for slow work (a file, a command, a network call) to finish. ({ path }) => … is a small function whose argument is an object, unpacking its path property, a bit like lambda args: … args["path"]. Backtick strings with ${…} are f-strings. const names a value you won't reassign; let one you will.

Copy the code into a scratch file, or onto paper, and annotate it:

  1. Mark the line where the model is called. What does it receive, and what does it send back?
  2. Mark the tools. Which one is the most dangerous? What in this file limits what it can do?
  3. Mark the approval check. Which calls skip it? What one-line change would turn this into an "approve everything" mode?
  4. Mark where each result goes back into the context. What would the model know without that line?
  5. Find where AGENTS.md enters. Is there any line of code that enforces what it says?
  6. What stops the loop if the model never says finish?
  7. Where have you met the edit tool's "exactly once" rule before?

✅ Checkpoint: your annotated copy marks the model call, the five tools, the approval check and the line that feeds results back, and you can say in one sentence why AGENTS.md is advice, not enforcement, using this code as evidence.

Wrap up Studio B ​

  • ☐ First feature on the feature/ac1 branch, published to GitHub, with a test that failed first and passes now (or a clear note of where you stopped).
  • ☐ PROMPTS.md has an agent entry with evidence and a teach-back.
  • ☐ Exit ticket done.
  • ☐ Stop your Codespace.

Troubleshooting ​

ProblemWhat to do
Be the Agent: edit says the old text "appears 3 times"The text isn't unique. Quote more of the line, for example the whole expression
Be the Agent: edit says "not found"The text doesn't match exactly: check spaces and quotes, and don't include line numbers from read_file
Be the Agent: bash: !…: event not foundThe text contains !. Pick a different piece of text to quote
No Agent option in Copilot ChatCheck you're signed in to GitHub and Copilot is enabled; update the Copilot Chat extension; reload the window (F1 → "Reload Window")
Copilot says you're out of creditsAgent work stops until the monthly reset. Switch to a fallback agent from the Tool Handout, or finish the feature yourself using Ask mode for advice. See I ran out of free credits
The agent ignores AGENTS.mdCheck Use AGENTS.md file is on and the file is in the top folder. Or start your prompt with "Read AGENTS.md first". Remember it's advice: approvals are what actually stop it
The check-first test passes before any code existsIt isn't testing the new behavior. Read it: does it call the new function and check the result AC1 describes? Ask for a stricter test, or write it yourself
The agent says tests pass, but npm test shows failuresBelieve your terminal, not the agent. Paste the real output back to it; if it fails twice, apply the two-strikes rule: new session, better prompt
The agent changed a testDiscard that change (Source Control → right-click → Discard Changes) and tell it: "Don't change tests/. Fix the code so the existing test passes."
The agent changed files you didn't ask aboutLook at the diff. Revert unwanted files with Discard Changes, or go back to your "before" commit. Then check your Scope section
The agent wants to install a packageStop. Check the package exists and is the one you meant on npmjs.com (Safety Contract, rule 6), and ask whether you really need it. The starter needs none
