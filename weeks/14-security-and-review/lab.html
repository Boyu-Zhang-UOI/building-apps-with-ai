Week 14 lab — Sweep, maintain, review ​

Two studios. Studio A: watch an agent get tricked by a file, sweep your capstone for security problems, and write a one-paragraph threat model of one feature. Studio B: change your own code with the AI switched off, then review a classmate's pull request and compare your review with an AI's. Do the Core parts first. If time parts are optional. Work in the Safe Loop and commit after every part.

AI-use key: 🟢 AI on: use AI freely, in the Safe Loop · 🟡 AI limited: the AI may explain and critique, but you decide and write · 🔴 AI off: no AI tools at all, including code completions.

What you need: your capstone repo in a Codespace, with git status clean; your Supabase project awake (restore it if paused); and (Studio B) your review partner.

WARNING

Everything here runs against your own capstone, or a classmate's pull request with their consent. Never point these tools at a database or site you don't own. Use made-up data only.

NOTE

Oral walkthrough 3 runs alongside this week's studios (10 minutes, 🔴 AI off): during Studio A's Parts A1–A2 and Studio B's Part B3. When you're called, commit your work, close AI chat panels, take your laptop to the walkthrough table, then come back and carry on where you stopped. No slot in class? Yours is in an office-hour slot this week (what to expect).

The prompt-injection demo (10 min) ​

Your instructor runs a 7-minute demo: an agent is given an innocent task in a small app whose files hide an instruction meant for the agent. Watch whether it obeys, warns or ignores it. The planted instruction is harmless; it only asks for a text file and a code comment.

Then discuss with a neighbor (3 min): which parts of the lethal trifecta (private data, untrusted content, a way out) does your capstone agent have, and what keeps it from having all three? Note your answer: it goes in section 6 of your checklist in Part A1. Safety contract rule 9 applies: when an agent reads untrusted content, approvals stay on and no secrets are within its reach.

Want to try it yourself? The Prompt-injection demo kit is optional and self-paced; run it only in a fresh Codespace, never in your capstone.

Part A1 — Security sweep (Core, 28 min) ​

🟢 AI on for explaining results. Run the top of your capstone's SECURITY_CHECKLIST.md (from the template) against your capstone. Tick each item and write one line of evidence.

  1. Secrets, including old commits (7 min). In your capstone repo:

    bash
    npm run check:secrets

    The scan reads your files and your whole git history. A key found in an old commit is still public, because anyone can read the history. If it finds one, revoke the key and make a new one (I committed a secret); deleting the line isn't enough. Then confirm .env is in .gitignore, .env.example holds only placeholders, and nothing under public/ starts sb_secret_.

    ✅ Checkpoint: no findings, and you can say where each key lives and why.

  2. Packages (7 min).

    bash
    npm audit

    It works because the starter commits a package-lock.json (a lockfile: the exact list of package versions, like a fully pinned requirements.txt in Python). If you see ENOLOCK, run npm install once and commit the package-lock.json it creates. Then check every dependency in package.json on npmjs.com (it exists, has real downloads and a real repository), and every library your page imports from a CDN:

    bash
    grep -rn "https://" public/ --include=*.js

    Each import should name the package you meant, with a version in the URL. The starter's db.js pins an exact version (@2.118.0, all three numbers), so nobody can swap the code under you. When you update it, change the number on purpose and test again. Real packages get hijacked too, so the safety contract says: install only what the plan named, and pin the version. A package you can't find on npmjs.com may be one the AI invented (what to do).

    ✅ Checkpoint: no high or critical audit issues you can't explain, and every package and CDN import is one you meant.

  3. Cross-site scripting (XSS) (10 min).

    bash
    grep -rn "innerHTML" public/

    For each hit, ask: can user-typed text reach it? If so, switch to textContent. Then, on the live site, type <img src=x onerror=alert(1)> into every input. No alert box should appear. If your app saves data, reload after saving the payload: text stored in a database reaches every visitor, so it must stay inert there too.

    ✅ Checkpoint: the payload shows as plain text, before and after a reload.

  4. Record it (4 min). Fill in the evidence lines, including the database line (every table that grants access to anon or authenticated has RLS on and at least one policy) and section 6: which parts of the trifecta your agent setup has, from the demo discussion. Anything you found goes in "What I found and fixed"; fix it in the Safe Loop now or in homework.

Part A2 — A threat model for one feature (Core, 10 min) ​

🟡 AI limited: you write the paragraph; afterwards the AI may point out misuses you missed.

Pick the feature most worth attacking: usually the one that saves data or calls a paid API. In the ## Threat model section of your SECURITY_CHECKLIST.md, write one paragraph that answers three questions:

  • Who could misuse it? (A curious visitor, a script using your publishable key, a classmate, a bot.)
  • How? (Flood it, post a huge or harmful entry, read or change someone else's rows, run up your AI bill, inject a script.)
  • What stops them? Point to the exact line, policy or setting. Then say what doesn't stop them yet.

For example:

Guestbook (public.messages). Any visitor, or a script using the publishable key from my page's source, could post thousands of messages, post a script tag, or edit or delete other people's messages. RLS limits each message to 1–280 characters, anon has no update or delete grant (supabase/policies.sql), and the page shows messages with textContent (public/app.js). Nothing yet limits how many messages one visitor posts; that's in my README's Known issues.

Then, if you like, ask the AI to find gaps:

text
Goal: Point out misuses of this feature that my threat model misses.
Context: A small web app (plain HTML, CSS, JavaScript; Supabase). My threat model and the
feature's code and policies are pasted below.
Constraints: Don't rewrite my paragraph. List at most three misuses, and for each, the file or
line that would stop it, or say that nothing does.
Done when: I can decide for each one whether to fix it now or list it as a known issue.

✅ Checkpoint: your checklist ends with a threat-model paragraph that names who, how, and the file or policy that stops them, plus at least one thing that doesn't yet.

Exit ticket (10 min) ​

Do the week 14 exit ticket now, AI off (🔴). It's here, not in Studio B, because Studio B is full of AI-off work. It's graded on completion, not correctness.

Troubleshooting (Studio A) ​

  • npm run check:secrets isn't a script: your repo didn't start from the capstone starter. Copy scripts/check-secrets.mjs and the script line in package.json from the capstone starter, or ask your instructor.
  • The scan finds a key in an old commit: revoke it at the provider and make a new one, put the new one only in .env and Vercel's environment variables, and record it in "What I found and fixed". Don't try to rewrite history.
  • npm audit lists issues: read which package and whether it's a development tool or something your site runs. Explain each high or critical one in your evidence line, or update the package on purpose and run npm test.
  • innerHTML in code you didn't write: if it only ever shows fixed text from your own code, it's fine; say so in your evidence. If user or database text can reach it, switch to textContent.
  • The alert appears: you've found real XSS. Switch that line to textContent, commit, deploy, and repeat the test, including the reload.

Part B1 — AI-off maintenance task (Core, 30 min) ​

🔴 AI off. Can you change your own app without the AI? In one study, most students who had used AI freely couldn't (Sankaranarayanan). This is a rehearsal for the Modify part of walkthrough 3, and it's graded on effort, not on finishing.

Set up (5 min):

  1. Turn Copilot off (how) and close every AI chat tab. It stays off through Part B2.

  2. Check git status shows nothing to commit, then make a branch:

    bash
    git switch -c maintenance-task

  3. Your partner (or your instructor) picks one change request for you from the cards below and words it for your app. You do the same for them.

Work (25 min): make the change by hand. Allowed: your code, the running app, DevTools, git, MDN Web Docs and the course Glossary. Not allowed: Copilot, chat assistants, or AI answer boxes in search results.

Change-request cards (small on purpose; adapt the words to your app):

  1. While a save or request is in flight, the button says "Saving…" and can't be clicked twice.
  2. Show a count next to the list's heading ("3 items"), and keep it right after adding.
  3. Reject input longer than [a number your partner picks] characters, with a visible message.
  4. Show the newest entry first instead of the oldest.
  5. Add a "Clear" button that empties the text box (not the saved data) and puts the cursor back in it.
  6. Change the empty-state message to [wording your partner picks], and hide it when there's data.
  7. Trim spaces from what the user typed before it's saved, and add one automated test for that.

Cards never touch supabase/policies.sql, keys or deployment settings. Done early? Add an automated test for your change, if its logic lives in public/lib/ or can be moved there.

Finish: test the change yourself, then let your partner try it (2 min). Commit it on the branch if it works, or leave it uncommitted and git restore . if it doesn't. In PROMPTS.md, add a short "AI-off maintenance task" entry: the request, what you changed, how long it took, and what you had to look up. How it felt goes in this week's reflection on Canvas.

✅ Checkpoint: you tried the change for the full time with the AI off, and recorded what happened.

TIP

Frozen? Find where the relevant text appears in index.html, then search app.js for that element's id. That's usually where the change goes.

NOTE

Working alone? Your instructor sends you a card at the start. See Self-paced path for the other substitutions this week.

Part B2 — Peer review as a pull-request review (Core, 25 min) ​

🔴 AI off for your review. You review the pull request your partner pointed you to (a proposed change on a branch, shown as a diff, that's reviewed before it joins main). They review yours.

Getting access (5 min). Capstone repos are public, so you don't need to be added: open your partner's repo on GitHub → Pull requests → the pull request they point you to. Anyone with a GitHub account can comment on a public repo's pull request.

  • Their pull request is already merged? Open it from the Closed filter; the Files changed tab still works. Or they open a new small one now.
  • Their repo is private? They add you under Settings → Collaborators for this week, and remove you afterwards. Collaborators can push, so they should also turn this off once the review and handoff are done.

Review on GitHub (20 min).

  1. Open Files changed and read the whole diff first.
  2. Use the headings of CODE_REVIEW.md template as your guide: does it do what their SPEC.md says (try it on their live site)? Can you explain one function in plain English? Safety: secrets, innerHTML, grants and RLS, packages. Their threat model is a good map of what to check.
  3. To comment on a line, hover over it and click the + button (or move to the line and use the comment button on its row), write the comment, and choose Start a review. Point to the line, explain why, and suggest a fix.
  4. When you're done, click Review changes (or Submit review), choose Comment, write a two-line summary, and submit. Menus move; ask a classmate if you can't find it.

Keep comments about the code. No grades, no names other than GitHub usernames.

The graded review is the written one on Canvas, using the CODE_REVIEW.md headings. You start it in Part B3 and finish it in homework. Share it with the author privately (a Canvas comment or email), never as a file or issue in their repo.

✅ Checkpoint: your partner's pull request has your submitted review with at least three located comments.

NOTE

Working alone? Review the practice pull request your instructor assigns; it has known issues to find.

Part B3 — Project time (15 min) ​

Copilot can go back on now. Walkthrough slots run during this part.

  1. Core: compare with an AI review (10 min). 🟢 AI on. Ask an AI to review the same pull request:

    text
    Goal: Review this pull request for bugs, security issues and unclear names.
Context: I'll paste the diff below. It's a small web app (plain HTML, CSS, JavaScript; Supabase).
Constraints: Be specific: point to lines. Separate real problems from style opinions.
Done when: You've listed the issues you're most confident about, worst first.

    Start your written review on Canvas with the compare table from CODE_REVIEW.md: real problems, false alarms and misses, for you and for the AI. Note one thing the AI caught that you didn't, and one the other way round.

  2. If time: Milestone 2 work. Read the review you received and start on its most important issue (homework Part 3), or, if you and your partner are both ready, start the handoff test now, while you're in the same room.

Troubleshooting (Studio B) ​

  • Copilot still suggests code during the maintenance task: completions are a separate setting from chat. Check both (how).
  • Your change broke the app and time is nearly up: git restore . puts the files back; the attempt still counts. Write what you tried in PROMPTS.md.
  • You can't find your partner's pull request: check the Closed filter, or ask for the link. A repo with no pull requests at all means the work went straight to main: they open a small new one now.
  • There's no + button next to a line: you're on the Conversation tab. Switch to Files changed.

Wrap up ​

  • Commit everything: sweep fixes, your SECURITY_CHECKLIST.md evidence and threat model, and the maintenance-task branch if the change worked.
  • Update PROMPTS.md template: teach-backs for agent commits, and the maintenance-task entry.
  • Walkthrough 3 not done yet? Check your slot on Canvas: it must be this week.
  • Homework: Week 14 homework — Milestone 2: secure it, review it, hand it off.
