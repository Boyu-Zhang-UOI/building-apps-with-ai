Week 4 — Undo, Compare, Explain ​

Save points only matter if you use them: break your game and bring it back, judge two AIs against your own check, and explain and test code you didn't type.

Learning objectives ​

By the end of this week you can:

  1. Restore an earlier working version of a file from its History, as a new commit, and explain why nothing is lost.
  2. Judge two AI models' answers to the same prompt against a "Done when" you wrote first.
  3. Explain a function in someone else's code without AI.
  4. Rewrite a weak prompt in four parts that someone else could check in a minute.
  5. Test a pure function from your game with Node's built-in test runner, and watch the test fail and pass.
  6. Move a function into a JavaScript module and use it from your game.
  7. Build a feature with check first and teach back.

Before class ​

  • ☐ Your game's last commit is a working version. If your last step is half-done, finish it or restore it before Studio A.
  • ☐ You can sign in to two chat assistants from the Tool Handout, with privacy settings done. Under 18? Your instructor will say which second assistant to use.
  • ☐ Before Studio B: pick the function in your game you'll test. The table in lab Part B2 suggests one for each game. Check that you can still open a Codespace (GitHub Codespaces; you did it once in the week 0 setup).

Key ideas ​

If you are working through this week on your own, read this section, then do the lab. The self-paced path says what to do instead of the pair activities.

Going back is calm, not scary ​

Last week you made a save point after every working step. This week you use one. You open the file's History on github.com, find the last commit that worked, and commit that version again. Nothing is erased: the broken commit stays in the history, with the restore on top. That's what git revert does, and you'll type the real command in week 8. Going back to a working version is one of the six skills you must show without AI, because AI tools can break things fast: in 2025 an AI agent deleted a company's production database, then wrongly claimed it couldn't be rolled back (Fortune).

Two models, one prompt ​

Different assistants give different answers to the same prompt. You judge them against your own "Done when", written before you look, not by which looks cooler, and not by what the AI claims. Which model "wins" changes from month to month; being the judge is the skill that lasts.

If you can explain it, you own it ​

In the peer explanation swap you explain one function in a classmate's game, with 🔴 AI off. That's the golden rule from last week's reading in practice, and it's how the course checks understanding: in the oral walkthroughs from week 8, you explain your own code without AI.

Writing the prompt is the skill ​

The prompt makeover asks you to rewrite four weak prompts yourself, without AI. A good rewrite has one goal, puts in the context the AI can't see, protects what already works, and has a "Done when" someone else could check in under a minute.

A test is a check that runs itself ​

So far your checks were things you tried by hand. An automated test is code that checks your code, in a second, every time you run it. The easiest code to test is a pure function: it uses only its inputs and returns a result, with no page, timers, random numbers or storage. You'll move one from your game (an average, a score rule, a collision check) into its own file, a module, and test it with the runner built into Node.js, which runs JavaScript outside the browser. Like pytest, with nothing to install.

Two rules come with tests. Watch it fail: a test you've never seen fail might not check anything, so you break the code on purpose once (red/green testing). Never change a test just to make it pass: if a test seems wrong, decide yourself, and write down why. From week 6, check first means writing a test like this before asking for the code.

Understanding check ​

  • In Studio B: the peer explanation swap. You explain one function in a classmate's game, with 🔴 AI off, and they confirm or correct you.
  • At the end of Studio B: the Week 4 exit ticket (🔴 AI off, scored for completion). Expect: how to get back to a working version; when one function in your game runs; what your first test checks and what change would make it fail; one question about the home page you published in week 2.

Homework ​

About 5 hours of core work plus the journal; details on the homework page. Project time: one more feature in 3+ save points, "Done when" first, a teach-back before each commit. Homework: a restore drill (🔴 AI off), the rest of the prompt makeover (🔴 AI off for the rewrites), and making your game use the tested function. Journal: PROMPTS.md; the reflection on Canvas (🔴 AI off). Stretch: a test written before the code, a second feature or a second tested function.

Graded on effort and completion of the core tier (rubric).

If a tool is down ​

ProblemWhat to do
Your main assistant is down or you hit a limitUse a fallback from the Tool Handout, pasting your current game/index.html (out of credits)
Only one assistant worksCompare two fresh chats in the same assistant
Codespaces won't start, or you're out of hoursRun the test with Node.js on your own computer (local setup), or watch a neighbor's today and run yours at home
GitHub is downPeer swap and makeover first; restore and test later with the lab steps
