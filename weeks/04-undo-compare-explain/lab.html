Week 4 Lab — Undo, Compare, Explain ​

Goal: in Studio A, break your game on purpose and go back, then compare two AI models on its next change. In Studio B, explain a classmate's code without AI, write your first automated test for a function in your game, and make over a weak prompt. Time: Studio A lab about 40 minutes, Studio B lab about 60 minutes. You need: your game at /game/ with its working-step commits from week 3, two chat assistants (see the Tool Handout), and in Studio B a Codespace on your home-page repository (or Node.js on your own computer).

AI-use key: 🟢 AI on: use AI freely · 🟡 AI limited: the AI may comment or hint, but the work is yours · 🔴 AI off: close the AI tabs and work alone.

Studios are graded on effort, not polish (rubric): a part that didn't work, with the exact error and what you tried, still counts.

Stuck for more than 5 minutes? Check Troubleshooting, ask a neighbor, then raise your hand. Using a screen reader or only a keyboard? The Screen reader and keyboard guide covers GitHub and VS Code in a Codespace.

Need the AI today? Start a new chat and paste in your current game/index.html from GitHub first: the AI doesn't remember last week.

Words you'll use this week ​

WordMeaning
RestorePutting a file back the way it was in an earlier commit, as a new commit
git revertThe git command that does the same thing: a new commit that undoes an earlier one (revert)
Pure functionA function that uses only its inputs and returns a result: no document, no timers, no Math.random(), no localStorage (pure function)
ModuleA JavaScript file that shares functions with export; other files use them with import (module)
Node.jsA program that runs JavaScript outside the browser, for example in a terminal (Node.js)
TerminalA text window where you type commands and read their output (terminal)

Studio A — Undo and compare (75 min) ​

The studio opens with a recap, the concept talk and a live demo (30 minutes), then:

PartWhat you doTimeCore or If timeAI use
A1Break it on purpose, then go back20 minCore🟢 AI on for the break · the restore needs no AI
A2Two models, one prompt20 minCore🟢 AI on · your "Done when" first
A3Plan your homework feature5 minIf time🟢 AI on for the plan

The studio ends with a checkpoint share: the hash you restored from, and which assistant won your comparison.

Part A1 — Break it on purpose, then go back (20 min) ​

Why: this is the most important part of the week. You'll see that a commit really is a save point, and that you can undo a disaster calmly.

Before you start, make sure your last commit is a working version of your game. (If it isn't, fix it or restore it first, and commit.)

Break it on purpose. Pick one:

  • Accept a vague, unreviewed change. Ask for it, and paste the result without testing it:

    text
    Make the game much more exciting. Change whatever you like.

  • Delete a line by hand. In the <script> section, delete a line containing } or a line that starts with if.

  • Change a number to something silly. Set a speed to 1000 or a grid size to 2.

Commit the broken version as Experiment: unreviewed change. A minute later the live game is broken, or different in ways you didn't choose. (Still works? Delete a line by hand and commit again.)

Go back to the last working version. Do this on github.com, in a new tab:

  1. Open your repository, then the game folder, then index.html.
  2. Click History (top right of the file, with a clock icon). You'll see every commit that changed this file, newest first. Your messages make this list readable.
  3. Find your last working commit (for example Step 5: …). Next to it is a short hash like 4f2a9c1. Copy it (there's a copy button) and paste it into your scratch note.
  4. On the same row, click the <> button (Browse repository at this point). You're now looking at your repository as it was then: the branch button near the top shows the hash instead of main.
  5. Open game/index.html and click Copy raw file (two overlapping squares, top right of the code).
  6. Go back to the present: click the branch button and choose main (or click your repository's name at the top). Open game/index.html again.
  7. Click the pencil icon (Edit this file). Select all the code, paste, and click Commit changes…. Use the message Restore working version from 4f2a9c1 (with your hash), and commit. No Assisted-by: line: a restore isn't AI-written.
  8. Wait a minute and check your live game. It's back.

Open History again. Every commit is still there, including the broken one: you added a new save point that puts the file back. That's exactly what git revert does, and you'll type the real command in week 8.

IMPORTANT

Your github.dev tab doesn't know about the commit you just made on github.com. If you have one open, check that its Source Control shows no pending changes (if it does, discard them: they're the broken version). Then close the github.dev tab and reopen it by pressing . on your repository page. Otherwise you'll be editing an old copy.

✅ Checkpoint: your file's History shows your step commits, Experiment: unreviewed change and Restore working version from …, and your live game works again.

Part A2 — Two models, one prompt (20 min) ​

🟢 AI on · 🔴 AI off for your "Done when".

Different models give different answers to the same prompt. Here you see how different, and judge them against a check you wrote first.

  1. Check first. Pick your game's next change (a fix from your play-test or edge-case list, or a small improvement) and write its "Done when" in your scratch note yourself, before you ask any AI.

  2. Write a four-part prompt for it, with your complete current game/index.html (Copy raw file on github.com) as Context and your "Done when" at the end. Send the exact same prompt to both assistants, each in a new chat.

  3. Test both results against your "Done when":

    • In an assistant with a live preview, test it there.
    • In an assistant without one, copy its file into a new file game/compare.html in github.dev, commit it as Compare: next change from [assistant] (with an Assisted-by: line), and open https://[your-username].github.io/game/compare.html a minute later.

  4. Fill in this table in your scratch note:

    QuestionAssistant AAssistant B
    Meets the "Done when"? (test it; don't take its word)
    Kept everything that already worked?
    Followed the constraints (one file, no libraries, complete file)?
    Added anything you didn't ask for?
    Which one could you explain to a classmate?

  5. Keep the better version: paste it into game/index.html, test, read the diff, and commit it as [what changed] (version from [assistant]), ending with Assisted-by: [assistant].

Only one assistant works? Send the same prompt to two fresh chats in the same assistant. You'll still see how much answers vary.

✅ Checkpoint: the winning version is committed with an Assisted-by: line, and your table says which assistant won and why.

Part A3 — Plan your homework feature (5 min, if time) ​

🟢 AI on for the plan.

Your homework adds one more feature in at least three save points (homework task 1). Start it now:

  1. Check first: write the feature's "Done when" yourself, in your scratch note, before you ask the AI anything.
  2. Then ask for a plan: Don't write code yet. Propose 3 small steps to add [feature] to my game, each with a "Done when" line. Here is my current game/index.html: [complete file]. Compare its plan with your "Done when".

Checkpoint share (end of Studio A) ​

Post one line where your instructor asks: the hash you restored from, and which assistant won your comparison and why (for example "Restored from 4f2a9c1; B won: it kept my controls"). Stuck? Post the exact blocker instead.

Working alone? Write the same line in your scratch note.

Part B1 — Peer explanation swap (15 min) ​

🔴 AI off. Explaining code in your own words is how you show you understand it, and it's one of the six skills you must show without AI.

In JavaScript a function often starts with function moveSnake( or const moveSnake = ( (an arrow function, like a Python lambda that can hold many lines). It runs when something calls it: a click, a key press, a timer or another function.

  1. Pair up and swap two links: your live game and your repository.
  2. Play your partner's game for a minute.
  3. On github.com, open their game/index.html and pick one function from the <script> section: not the longest, not a one-liner.
  4. Take 4 minutes to write down, alone:
    • Name: the function's name.
    • When it runs: what calls it?
    • What it does: at most three plain-English sentences, about what it means in the game, not line by line.
    • If you deleted it: what would break in the game?
  5. Explain it to your partner in 2 minutes. They confirm or correct you. If they aren't sure either, you've both found something worth learning: the game's author asks the AI about it after class and logs what they learned in PROMPTS.md.
  6. Swap roles.

Working alone? Pick a function in your own game, write the four answers without AI, and explain it out loud to a friend or record yourself on your phone. Only afterwards, check your explanation with the AI.

✅ Checkpoint: you explained one function in someone else's game, and they confirmed or corrected it.

Part B2 — Your first automated test (35 min) ​

🟡 AI limited. The worked example gives you the code. Your assistant may explain an error message or the test output; it doesn't write your tests or move your function for you. 🔴 AI off for your own test in step 7.

Why: until now your checks were things you tried by hand. An automated test is code that checks your code in a second, so after every later change, yours or an AI's, you can check that nothing broke. You'll move one pure function from your game into a module, so Node can run it without a browser, and test it with Node's built-in test runner. You'll add three files to your home-page repository:

FileWhat it holds
package.jsonTells Node your files use modules, and what npm test should run
tests/logic.test.jsThe tests, written first
game/logic.jsThe function the tests check

If you know Python, most of it will look familiar:

JavaScriptPython
node --testlike pytest: finds files named *.test.js and runs them; built into Node, nothing to install
import { test } from "node:test";from ... import test; a file shares only what it marks export
assert.equal(actual, expected)assert actual == expected, but strict: it uses ===, so "5" isn't 5
assert.deepEqual([4, 4], [4, 4])needed for arrays and objects: two separate arrays are never ===
assert.ok(a < b)assert a < b: passes when the condition is true
times.length, times.reduce(…)len(times), sum(times)

1. Open a Codespace (3 min). On your home-page repository's page, click Code → Codespaces → Create codespace on main (how). Open the terminal at the bottom (Ctrl+` if it's hidden). Node is already installed. On your own computer, with Node.js 20.12 or later (local setup), use a terminal in your repository's folder instead.

2. Pick your function (3 min). It must be pure. Yours may have another name, or the calculation may be buried in a bigger function; then you'll write it as a function of its own in step 5.

GameFunction to testExample checks (input → expected)
Reaction timeraverageTime(times) (the worked example below)[200, 300, 400] → 300
Whack-a-molemoleUpTime(secondsLeft): how long a mole stays upthe result at 5 seconds left is smaller than at 30
Memory matchisMatch(first, second) for two card objectssame emoji, different cards → true; the same card twice → false
Typing speed testwordsPerMinute(characters, seconds)(50, 30) → 20
Simon saysisCorrectSoFar(sequence, moves)([1, 2, 3], [1, 2]) → true; ([1, 2, 3], [1, 3]) → false
SnakehitsWall(head, size)({ x: 19, y: 5 }, 20) → false; ({ x: 20, y: 5 }, 20) → true
Pongwinner(left, right)(5, 3) → "left"; (4, 4) → null
Flappy-styleoverlaps(a, b) for two rectangles { x, y, w, h }a bird inside a pipe → true; a bird clear of it → false
BreakoutbounceAngle(hitX, paddleX, paddleWidth)hitting the middle → 0; hitting the left half → a negative angle
2048slideRowLeft(row)[2, 2, 4, 0] → [4, 4, 0, 0]; [2, 2, 2, 2] → [4, 4, 0, 0]

Write down two or three input → expected pairs from what the game should do (your plan's "Done when"), not from reading the code: a test copied from the code agrees with its bugs.

3. Create package.json (2 min) in the top folder of your repository, next to your home page's index.html (Explorer → New File):

json
{
  "private": true,
  "type": "module",
  "scripts": {
    "test": "node --test"
  }
}

"type": "module" lets Node read import and export; "test" is what npm test runs. There's nothing to install.

4. Write the tests first, and see red (7 min). Create a new file and type tests/logic.test.js as its name (that makes the folder too). Here is the worked example for the Reaction timer:

js
import { test } from "node:test";
import assert from "node:assert/strict";
import { averageTime } from "../game/logic.js";

test("averages three attempts", () => {
  assert.equal(averageTime([200, 300, 400]), 300);
});

test("rounds to the nearest millisecond", () => {
  assert.equal(averageTime([200, 201]), 201);
});

test("one attempt is its own average", () => {
  assert.equal(averageTime([250]), 250);
});

Write yours the same way: your function's name in the import line, and one test(…) per pair from step 2, named for what should be true. Then, in the terminal:

bash
npm test

It fails, with a message that it cannot find the module game/logic.js, and fail 1 near the bottom. That's correct: the check exists and the code doesn't yet.

5. Move your function into a module, and see green (8 min). Create game/logic.js. Copy your function from the <script> section of game/index.html into it, and put export in front (export function …, or export const … for an arrow function):

js
// Pure functions: they use only their inputs and return an answer.
// No document, no timers, no Math.random(), so Node can test them.

export function averageTime(times) {
  const total = times.reduce((sum, time) => sum + time, 0);
  return Math.round(total / times.length);
}

If your function reads a variable from outside itself (a GRID_SIZE, the current score), make it a parameter instead. Run npm test again: a ✔ for each test, pass 3 and fail 0.

A test fails? Read what it expected and what came back: either your expectation or your game is wrong. Decide which yourself, and write down why. Never change a test just to make it pass. For now the game still uses its own copy of the function; homework task 4 makes it use this tested one.

6. Break it on purpose (3 min). Make one small wrong change in game/logic.js and run npm test. In the worked example, Math.round → Math.floor fails only "rounds to the nearest millisecond", expecting 201 and getting 200. For yours, flip a comparison (>= to >) or change a number by one. Read the failure, change it back, run again: green. A test you've seen fail is one you know really checks something.

7. One test of your own (5 min, 🔴 AI off). Add one more test, for an edge case you think of yourself: empty input, zero, exactly on a boundary, a negative number, the same thing twice. Before you run it, write in your scratch note whether you think it will pass. In the worked example, averageTime([]) (no attempts yet) returns NaN, because it divides 0 by 0:

js
test("no attempts yet gives 0, not NaN", () => {
  assert.equal(averageTime([]), 0);
});

That test fails: it has found a real edge case, and what the game should show before the first attempt is your call. If your own test fails, fix the function now if it's quick, or in homework task 4.

8. Commit, push and stop (4 min). In Source Control, commit with the message Add first automated test for [your function] (choose Yes if asked to stage all changes; add Assisted-by: only if an AI helped write it), then Sync Changes to push. Stop the Codespace: Command Palette (Ctrl+Shift+P / Cmd+Shift+P) → Codespaces: Stop Current Codespace. Close any github.dev tab: it doesn't know about these commits.

✅ Checkpoint: npm test shows your tests passing (and your own test passing, or failing for a reason you've written down), you've watched one fail on purpose, and your commit is on github.com.

Part B3 — Prompt makeover workshop (10 min) ​

🔴 AI off. Writing a good prompt is the skill, so you write these yourself.

Worked example (your instructor walks through it, 2 min).

  • Weak prompt: make my website better

  • Situation: your home page's text is hard to read on a phone and the sections run into each other.

  • Rewrite:

    text
    Goal: Make my home page easier to read on a phone.
Context: Here is my current index.html: [complete file]. On my phone the text is tiny and the sections run together.
Constraints: Don't change any text or colors. CSS changes only. Give me the complete file.
Done when: On a 375-pixel-wide screen, body text is at least 16 pixels, each section has clear space around it, and nothing scrolls sideways.

The four weak prompts. In the studio you rewrite A. You finish B, C and D for homework.

#Weak promptSituation
Afix itIn your Whack-a-mole game, the score goes up when you click an empty hole, not only when you hit a mole. You're starting a new chat.
Badd a leaderboardYou want your Pong game to show the top 5 scores. The game is one HTML file on GitHub Pages, with no server. (Hint: a leaderboard shared by everyone needs a server, which comes in week 9. What could work in this browser only?)
Cmake a to-do app with login, reminders, dark mode, drag and drop, sharing with friends and AI suggestionsYou want to start a project soon. (Hint: this is at least five projects. Rewrite it as a plan prompt for a first version, and say what's out of scope.)
Dmake it look more professionalYour home page uses five colors and three fonts, and you'd like a calmer, cleaner look.

Check a rewrite against these four questions:

  • ☐ It has one goal, not several.
  • ☐ Context includes the facts the AI can't see (the current code, what happened).
  • ☐ Constraints protect what already works.
  • ☐ Done when could be checked by someone else in under a minute.

In the studio: rewrite prompt A alone, on paper or in a note (5 min); you may invent reasonable details. Then swap with a neighbor, check each other's rewrite against the four questions, and suggest one improvement (3 min).

Working alone? Check your rewrite against the four questions yourself, then put it away for ten minutes and read it again as if you were the AI.

✅ Checkpoint: you have a four-part rewrite of prompt A that passes all four checks.

Before you leave Studio B ​

  • ☐ Your game's History shows the experiment and the restore, and one comparison commit with an Assisted-by: line.
  • ☐ Your test commit is on github.com, and your Codespace is stopped.
  • ☐ You did the Week 4 exit ticket (🔴 AI off). It's scored for completion, not correctness.

Troubleshooting ​

ProblemFix
Can't find HistoryOpen the file itself first (not the folder), then look at the top right of the code
Can't find the <> button in HistoryClick the commit message instead, find game/index.html in the diff, and use its … menu → View file
You restored the wrong versionNo harm done. Everything is still in History; restore again from the right hash
github.dev shows old code after the restoreClose the github.dev tab and press . on your repository page again
npm test says Missing script: "test" or can't find package.jsonpackage.json isn't saved, or isn't in the top folder. Run ls in the terminal: you should see package.json, index.html and game
Still "cannot find module", or does not provide an export named …Check game/logic.js is spelled exactly (lowercase), the test imports ../game/logic.js, export is in front of function, and the names match (case matters)
Cannot use import statement outside a module"type": "module" is missing from package.json
ReferenceError: document is not defined (or window, localStorage)The function isn't pure: it touches the page. Move only the calculation into logic.js, and pass the values it needs as parameters
A test of an array or object fails although the values look the sameUse assert.deepEqual instead of assert.equal
npm test never finishesSomething in logic.js starts a timer (setInterval, setTimeout) as the file loads. Keep only pure functions in it. Press Ctrl+C to stop
The test still passes after you broke the code on purposeSave the file (a white dot on its tab means unsaved), and check the test calls the function you changed
You hit an assistant's usage limitSwitch assistants and paste your current file from GitHub (out of credits)

If a tool is down ​

  • Main assistant down: use a fallback from the Tool Handout. Paste your current game/index.html from GitHub into the new chat first, because the new tool starts with an empty context window.
  • Only one assistant works: do the comparison in Part A2 by sending the same prompt twice to the same assistant in two fresh chats.
  • Codespaces won't start, or you're out of hours: use Node.js on your own computer (local setup), or watch a neighbor's screen today and run your own test at home (troubleshooting).
  • github.dev won't open: edit on github.com instead. Open the file, click the pencil icon, paste, then Commit changes… (the Assisted-by: line goes in Extended description).
