Week 12 Lab — Pull requests and agent code ​

Two studios. In Studio A you add one test by hand to your week 11 feature, then merge it into main through your first pull request. In Studio B you hunt a bug planted in agent-written code with the AI off, and start a second feature at the feature clinic.

AI-use key: 🟢 AI on: use AI, following the Safe Loop · 🟡 AI limited: only in the way the step says · 🔴 AI off: close AI chat and turn off completions.

This week's rules for agents: approvals stay on (never autopilot or skip-permissions modes); commit before and after every agent task; read every command before you allow it; the agent never gets your keys. Stuck at any point? See Troubleshooting at the bottom of this page.

The live demo: a pull request from branch to merge ​

Your instructor takes the branch from last week's demo all the way to main, while you watch for five things: the description says what, why and how it was tested; the checks run the tests on GitHub; Files changed shows the whole diff, read line by line; a comment goes on one line; and after the merge, git pull brings main up to date in the Codespace. You'll do exactly this in Part A1.

Part A1 — Branches and pull requests (40 min) ​

Core · 🔴 AI off for the test you write in step 2; otherwise no AI needed

Why: main is the version that's deployed, so it should always work. A pull request (PR) proposes merging a branch into main and shows the whole change as one diff, with the automated tests run on it, before it joins. From now on every capstone feature joins main through a pull request; in week 14 a classmate reviews one of yours.

  1. Where you are (2 min). In your capstone Codespace:

    bash
    git branch

    It lists your branches; * marks the one you're on. You should be on feature/ac1. If not: git switch feature/ac1. (In a new Codespace, the branch may not be listed yet; git switch feature/ac1 still finds it on GitHub.)

  2. Add one test by hand (15 min). Writing a criterion and its test without AI is one of the six skills you must show without AI. Think of one more edge case for AC1 (a name with spaces around it, the same name in different capitals, a name just over a length limit). Add it to SPEC.md as a new criterion, with the next free number, in WHEN … THE APP SHALL … form. Then type a test for it by hand in your test file, copying the shape of the tests already there, and run npm test.

    • If it fails, fix the code by hand until it passes.
    • If it passes straight away, say why (the code already handles it), and prove the test can fail: change its expected value for a moment, see it fail, change it back.

    Commit (no Assisted-by: line: you wrote it) and sync: git commit -am "Add test for names in different capitals", then Sync Changes.

  3. Open the pull request (6 min). On github.com, open your repository. A banner says your branch had recent pushes: click Compare & pull request. (No banner? Pull requests → New pull request, base main, compare feature/ac1.) Give it a title that says what it does, and a short description:

    markdown
    **What:** Reject empty and duplicate habit names (AC1, AC7).
**Why:** SPEC.md AC1; duplicates made the streak count wrong.
**How I tested it:** npm test (tests 14, pass 14); tried empty, duplicate and different-capitals names in the browser.
**AI use:** GitHub Copilot agent mode for the AC1 test and code; AC7's test by hand. Teach-back in PROMPTS.md.

    Click Create pull request.

  4. Checks (3 min). Your test workflow runs on the pull request. Wait for the green check. A red ✗? Click Details and read which test failed. If your capstone is on Vercel, a comment or check from Vercel links to a preview deployment of this branch: open it and try the feature before you merge.

  5. Review your own pull request (8 min). Click Files changed and read it as a reviewer would:

    • ☐ Only the files I meant to change. No .env, no stray files.
    • ☐ Every line is one I can explain.
    • ☐ No secrets, no leftover console.log lines or commented-out code.
    • ☐ The tests in tests/ changed only where I added one.
    • ☐ The description matches what the diff actually does.

    Leave at least one comment on a line (hover over the line → +), for example why a check is written the way it is. That's ordinary code review: keep comments about the code.

  6. Merge (3 min). Click Merge pull request → Confirm merge → Delete branch.

  7. Update your Codespace (3 min).

    bash
    git switch main
git pull
git log --oneline -5

    The log now shows your commits on main. If your capstone is on Vercel, the merge also redeployed it: open your production URL and try the feature live.

Pairs: your partner reviews instead (Files changed → Review changes → Approve), then you merge. Working alone? Self-review is exactly right; in week 14 a classmate or your instructor reviews a later pull request.

✅ Checkpoint: your first pull request is merged, the branch is deleted, and git log on main shows the feature. More detail: branches and pull requests in the Git Cheat Sheet.

Part A2 — Start the Goldfish test (10 min) ​

If time · 🟡 AI limited

Start homework task 1: paste only your SPEC.md into a fresh chat and log what it says it would build. The revision can wait for homework.

Wrap up Studio A ​

  • ☐ First pull request merged; main up to date in your Codespace.
  • ☐ A hand-written test for a new edge case, in SPEC.md and in tests/.
  • ☐ Codespace stopped.

Part B1 — Find the bug planted in agent-written code (25 min) ​

Core · 🔴 AI off for the Fixer

Why: the agent will write code that is almost right. In one study of 917 students, bugs planted in otherwise-correct AI code led students to fix the code themselves instead of asking the AI again, and those students did better on their next attempt (Pădurean et al.). Reading the failure and finding the line is one of the six skills you must show without AI.

Work in pairs at one computer: the Fixer's capstone Codespace, and a Planter.

  1. Fixer (2 min). On main, with git status clean, start a practice branch: git switch -c practice/bug-hunt. Turn the AI off (close Copilot Chat; turn off completions). Turn away from the screen.

  2. Planter (3 min). Open the file in public/lib/ that the agent wrote in week 11. Change one small thing that a test or the browser would catch: flip > to >=, change a number, remove a ! (JavaScript's not) or a .trim() (JavaScript's .strip()), or swap two variables. Don't touch the tests. Save, then commit it so the change doesn't show as unsaved: git commit -am "Practice". Say "ready".

  3. Fixer (12 min). Find it and fix it by hand. No AI, and no git diff, git log -p or git show (they'd show you the answer). Run npm test and read the failure from the top: which test, which file and line, what it expected and what it got. Open the function, reason about it, fix it, and run npm test until it shows fail 0. If no test fails, the bug escaped your tests: find it in the browser, and note in TESTS.md the test that would have caught it.

  4. Check (3 min). Now you may look: git diff main shows how your version differs from the original. Nothing, or an equivalent fix you can explain, means you found it.

  5. Clean up (2 min).

    bash
    git restore .
git switch main
git branch -D practice/bug-hunt

  6. Talk (3 min). Which clue found it fastest? Did you want to ask the AI? Swap roles in project time if you both want a turn.

Working alone or online? Let an AI plant the bug (🟢 AI on for planting only). Paste the function into a chat with: "Change exactly one small thing in this function so it has a subtle bug that a test could catch. Don't tell me what you changed. Reply only with the full changed function." Paste the reply over the function on your practice branch, commit it, close the chat, and do step 3 with the AI off.

CAUTION

Never "fix" a failing test by changing what it expects, unless SPEC.md says the test is wrong. One developer's "fix it" prompt changed a test's expected status from 200 to 500 so the test would pass, and the bug stayed (HN discussion).

✅ Checkpoint: the Fixer found and fixed the planted bug by hand, or knows which test was missing; the practice branch is deleted.

Part B2 — Feature clinic (25 min) ​

Core · 🟢 AI on: agent mode with approvals on · 🟡 AI limited for the criterion you write · 🔴 AI off for the teach-back

Why: two of the four capstone feature types, (c) a data visualization and (d) an external public API, need a pattern you haven't used yet. The capstone starter includes tested examples of both (feature patterns). Pick the station your pitch needs; the feature you start here is your homework feature.

Every station uses the same loop as week 11's first feature:

  1. Write the criterion in SPEC.md (🟡 AI limited: you write it).
  2. Start a branch from an up-to-date main: git switch main, git pull, git switch -c feature/[short-name].
  3. Check first: the test, in its own chat or by hand; see it fail; commit it.
  4. New chat: plan first, approve, build; approvals on.
  5. Green in your own terminal; tests/ unchanged; read the diff; try it by hand.
  6. Teach-back (🔴 AI off), commit with an Assisted-by: line, publish the branch, open a pull request, review it, merge it.

Today, aim to finish steps 1–3. The rest continues in project time and homework.

Station C — A simple chart ​

For capstones that draw a chart from their own data. Read A chart with no libraries in the starter README, then public/lib/chart.js and tests/chart.test.js. The helper draws a bar chart as SVG (a format for drawing shapes in a web page) from rows of { label, value }, and countBy can count things in your data for you. Most chart bugs are data bugs, so your job is the data preparation: the pure function that turns your app's records into those rows, which is the part you test first.

  • Decide what to chart: which numbers, grouped how (per day, per week, per category)? Keep it to one chart.
  • Example criterion: "WHEN I have logged sessions on three different days, THE APP SHALL show one bar per day, labeled with the day and its total minutes."
  • The helper adds a text description for screen readers. If the numbers matter, also show them as text (a list or a small table) next to the chart, so anyone who can't tell the bars apart gets the same information.

Station D — An external API route ​

For capstones that fetch live data from a public service. Read Data from a public API in the starter README, then api/weather.js, lib/weather.js and tests/weather.test.js. It's the external-API pattern from week 10, with tests that replace fetch with a fake (a mock), so they run offline. To use a different API, the README says to copy lib/weather.js and change the address and the step that simplifies the reply.

  • Pick your API. Read its terms: whether it needs a key, how many requests it allows, and whether you must credit it. (If it needs a key, the key goes in environment variables, and the feature counts as type (a) instead.)
  • Write the check-first tests with a fake fetch: a good answer, a service error or timeout, and bad input.
  • Example criterion: "WHEN the weather service doesn't answer within 10 seconds, THE APP SHALL show 'Weather is unavailable right now', and the rest of the page SHALL keep working."

Neither station fits? ​

If your capstone uses (a) an AI feature or (b) a database: for (a), adapt api/ask.js the way you did with your week 9 micro-app, and test the validation of any new input first. For (b), week 13 Studio A connects Supabase safely; today, build and test the pure logic for your data (for example, checking a new entry) in public/lib/. Either way, use the same loop.

✅ Checkpoint: your criterion is in SPEC.md, you're on a feature branch, and your check-first test fails for the right reason.

Part B3 — Project time (10 min) ​

Core · AI use as each task says

Use this time for whatever moves you forward most, with help from your instructor:

  • Keep going on your clinic feature, through the same loop, toward a reviewed and merged pull request.
  • Deploy, if your capstone isn't on Vercel yet: week 11 homework task 4.
  • If time: explain it to a classmate (🔴 AI off). Open the Files changed tab of the pull request you merged in Studio A and walk a neighbor through what the agent changed and why it works. They ask you about one line. A line you couldn't explain is the one to read again tonight (Explain any function you committed).

✅ Checkpoint: your clinic feature has a failing check-first test on its branch.

Wrap up Studio B ​

  • ☐ Planted-bug hunt done; practice branch deleted.
  • ☐ Clinic feature on its own branch, with a check-first test.
  • ☐ Everything committed and synced; Codespaces stopped.

Troubleshooting ​

ProblemWhat to do
git switch feature/ac1 says the branch doesn't existIt wasn't published last week. If you're in the same Codespace, it's still there locally: check git branch. Otherwise run git fetch, then try again; if it's still missing, ask for help before you redo anything
git switch says you have uncommitted changesCommit (or discard) them first, so every branch starts from a clean save point
No Compare & pull request bannerUse Pull requests → New pull request, base main, compare your branch. Check the branch was published (git push -u origin [branch])
The pull request's check is redClick Details to see which test failed, fix it on the same branch, commit and push: the pull request updates itself
No preview link on the pull requestYour capstone isn't connected to Vercel yet. Do week 11's deploy task; the next push to the branch gets a preview
The pull request says "This branch has conflicts"Stop and ask for help; don't let the agent "resolve" it blindly. See I have a merge conflict
git pull on main says "diverged"You committed on main in the Codespace while the pull request merged on GitHub. Ask for help before you force anything
You committed on main instead of a branchDon't let the agent fix it. git switch -c feature/[short-name] keeps the commits on a new branch; ask your instructor before you change main
Planted-bug hunt: no test failsThe bug escaped your tests. Find it in the browser, then add the missing test to TESTS.md (and, later, to tests/)
Planted-bug hunt: git branch -D says you're on that branchRun git switch main first
Station D: a test reaches the real service, or fails offlineThe test must replace fetch with a fake before calling your function. Copy the setup from tests/weather.test.js
Station C: the chart doesn't appearCheck that the element in index.html has the id you pass to renderBarChart, and that every value is a number of 0 or more. Open DevTools' Console for errors
