Week 13 — Data & Access Rules ​

A public key plus missing access rules equals a public database. This week you make that mistake on purpose, fix it, then connect your capstone to a database the safe way.

Canvas is the course's learning management system. Graded personal writing (your reflection) goes there, never in a repo.

Learning objectives ​

By the end of this week you can:

  1. Explain the difference between authentication (who you are) and authorization (what you are allowed to do), and say why authorization must be enforced on the server or in the database, never only in the page.
  2. Explain why a Supabase publishable key is safe in the browser only when row-level security (RLS) is on, and why a secret key never goes in the browser.
  3. Put a practice table in a vulnerable state, attack it with only its public key, then write RLS policies until your own attack fails.
  4. Tell the three kinds of "blocked" apart: no grant, refused by a policy, and 0 rows.
  5. Connect your capstone to Supabase with explicit grants and RLS policies in supabase/policies.sql, and prove with an attack that they hold.

Before class ​

Before Studio A (30 minutes at most):

  • ☐ Read this page.
  • ☐ Create a free Supabase account and a new, empty project called rls-lab on the free plan (Tool Handout), with any region and a database password you won't need again. It takes a minute or two to set up, so doing it now saves lab time.
  • ☐ Read case 12: UpGuard's 16,326 exposed Supabase databases.
  • ☐ Check Milestone 1: your capstone is deployed and your week-12 features went through pull requests. Behind? Tell your instructor: Studio A works without a finished capstone.

Key ideas ​

Authentication vs authorization. Authentication answers "who are you?" (signing in). Authorization answers "what are you allowed to see and do?" A signed-in user is still not allowed to read everyone's private notes. Karpathy's own example: an agent matched two accounts by email address instead of a stable user ID, a bug only an understanding human caught (September report).

Authorization must live on the server or in the database. Anything in the browser is public: a user can open DevTools, read your JavaScript and call your database directly. Hiding a button stops no one.

Supabase in one line. A Postgres database plus an automatic web API (the Data API), so your page can talk to the database directly with a key.

IMPORTANT

Not every key is a secret. The Supabase publishable key (starts sb_publishable_) and your project URL are public by design: they go in public/config.js, and anyone who loads your site can read them. That's safe only when RLS is on with the right policies. The secret key (starts sb_secret_) skips every access rule, so it lives only in server environment variables, never in public/, a repo or a chat. Your LLM key from week 9 is a secret too. Older projects also show legacy anon and service_role keys (long strings starting eyJ); they are deprecated, so use the new ones.

Two locks on every table. A grant decides whether a role, such as anon (anyone with the publishable key), may use a table at all. An RLS policy decides which rows that role may read or change. From 30 October 2026, new Supabase tables get no grants automatically, so the API answers "permission denied" until you add them (Supabase changelog). Always add grants and turn on RLS with policies together, in one file. Never "fix" a permission-denied error with a bare grant to anon: that rebuilds exactly the leak below.

RLS in plain words. Row-level security is a switch on each table. Off: anyone with a grant can read and write every row. On, with no policies: nobody using the public key gets anything. On, with policies: each request is allowed only if a policy says so, for example "anyone may read rows where is_public is true".

If you know Python or SQL: a policy's using (...) part works like a WHERE clause added to every query, so rows that fail it are invisible. Its with check (...) part works like an assert on every new or changed row. That's why a blocked update returns "0 rows" with no error, while a blocked insert raises one. So always check how many rows changed, not only whether there was an error.

This year's leaks. In September 2026 UpGuard found 16,326 Supabase databases with publicly readable tables; tables that agents create through the API start with RLS off (UpGuard). Platforms fail too: a missing ownership check in Lovable's project API let any free account read other users' code and database credentials (Sable). Full write-ups, including the 2025 cases (Lovable's missing policies, Moltbook, Base44): Case Studies. Week 14 covers the rest of the map: cross-site scripting, secrets in old commits, packages and prompt injection.

Understanding check ​

Complete the week 13 exit ticket at the end of Studio B, with AI off (🔴). You'll explain authentication versus authorization, say exactly where authorization is enforced in your app, say when a public key becomes a problem, and answer one question from memory about your first agent-built feature from week 11. Exit tickets are graded on completion, not correctness.

Homework ​

Homework: your second feature type through a pull request, section 3 of your checklist, PROMPTS.md and your reflection. About 5.5 hours.

If a tool is down ​

  • Supabase is down or won't create a project: follow the instructor's live demo and fill in the before/after table from it, then use Neon or Turso (database only, no sign-in; see Tool Handout), or keep data in the browser with localStorage for now. The idea (client vs server, authorization rules) is assessed, not the vendor. More: Troubleshooting: Supabase.
  • "Permission denied for table …": the table has no grant yet. Add the grant and RLS and policies together (lab Part B1), never a grant on its own.
  • Supabase project paused: free projects pause after about a week without activity. Open the dashboard and restore it; your data comes back.
  • The hosted attack page won't load: open attack.html from the RLS Attack Lab kit on your own computer, or serve the kit folder in a Codespace with python3 -m http.server 8000.
  • Codespaces quota or Copilot credits gone: the attack page runs in any browser; edit your capstone in github.dev; write the agent step by hand from the starter's feature pattern (I ran out of free credits).
  • Your capstone is behind: do the RLS lab, and the worked example on a practice branch. Persistence becomes your homework priority; book office hours early in the week.

Going further ​

  • Add Supabase Auth so each user sees only their own rows, or attack your own live site from the DevTools Console (both in the lab's Part B3).
  • Read case 16 in Case Studies (Lovable's missing ownership check) and write down which RLS policy would have answered "is this row yours?".
