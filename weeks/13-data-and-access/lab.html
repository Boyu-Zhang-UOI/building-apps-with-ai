Week 13 lab — Attack, fix, connect ​

Two studios. Studio A: break a practice database with its public key, then fix it with row-level security. Studio B: connect your capstone to Supabase the safe way, attack your own table, and wire up one feature with the agent. Do the Core parts first. If time parts are optional. Work in the Safe Loop and commit after every part.

AI-use key: 🟢 AI on: use AI freely, in the Safe Loop · 🟡 AI limited: the AI may explain and critique, but you decide and write · 🔴 AI off: no AI tools at all, including code completions.

What you need: a free Supabase account and the empty rls-lab project you made before class (Tool Handout), and (Studio B) your capstone repo in a Codespace. The attack page is hosted, so there's nothing to install for Studio A.

WARNING

Everything here runs against your own practice project and your own capstone. Never point these tools at a database or site you don't own. Use made-up data only.

Part A1 — RLS Attack Lab (Core, 45 min) ​

🟢 AI on, if you want explanations. Big idea: with the public key and no row-level security (RLS), anyone can read and change every row. You prove it, then lock it down. The lab runs whole, in this studio.

A1.1 Open your practice project (3 min) ​

  1. Open the rls-lab project you created before class in the Supabase dashboard.
  2. Didn't make one? Create a new project on the free plan now, call it rls-lab, pick any region and a database password you won't need again, and start A1.2 while it finishes setting up.

✅ Checkpoint: you see the project dashboard, with SQL Editor and Table Editor in the left-hand menu.

NOTE

Menus move. If a name here doesn't match what you see, ask your assistant "Where is the SQL Editor in the current Supabase dashboard?" or search the Supabase docs.

A1.2 Create the vulnerable table (7 min) ​

  1. Open SQL Editor → New query.
  2. Open setup.sql from the RLS Attack Lab kit, copy all of it, paste it in, and click Run. Supabase may ask you to confirm because the script contains drop table. Confirm: this is your practice project.
  3. Open Database → Advisors → Security. You should see an error called "RLS Disabled in Public", warning that anyone with your project URL can read, edit and delete all data in the table. The Table Editor may also mark the table Unrestricted.

✅ Checkpoint: the guestbook table has 6 rows, and Supabase is warning you that RLS is off. That warning is the whole point.

IMPORTANT

Supabase now protects new tables in two ways: tables made in the Table Editor get RLS on, and from 30 October 2026 new tables get no grants (no permission for the public roles to use them at all). setup.sql undoes both on purpose, with explicit grants and disable row level security, so the vulnerable state is the same in every project. Real leaks happen the same way: someone, or an agent, turns the protections off.

A1.3 Get your keys (5 min) ​

  1. Click Connect at the top of the dashboard, or go to Settings → API Keys.
  2. Copy two things into a scratch note (not a file in a repo):
    • the Project URL (looks like https://abcdxyz.supabase.co)
    • the publishable key (starts sb_publishable_)
  3. Leave the secret key alone (starts sb_secret_). You never need it in this course's front end.

NOTE

If you only see a legacy anon key (a long string starting eyJ), look for the tab with publishable and secret keys and create a publishable key there. Supabase is retiring the legacy anon and service_role keys by the end of 2026.

✅ Checkpoint: you have a Project URL and a publishable key in a scratch note.

A1.4 Attack the table with only the public key (12 min) ​

You use a tester page that does what any stranger could build in an afternoon.

  1. Open the hosted RLS attack page. It runs in your browser and talks straight to your Supabase project.
  2. Read the banner. Paste your Project URL and publishable key, leave the table as guestbook, and click Connect.
  3. Run each button and note the label the page gives each result (open How to read the results on the page for what each label means):
    • Read all rows: you see all 6 rows, including the 2 private notes (is_public = false).
    • Insert a row: works. Try again with is_public set to false: also works.
    • Update row #1: works; the message changes.
    • Delete newest row: works; a row disappears.

✅ Checkpoint: with only the public key, you read private notes and changed and deleted data. This is the state UpGuard found in 16,326 databases. Fill in the "Before fix" column in A1.6.

TIP

The page keeps your URL and key in memory only and never saves them. Click Forget key when you're done, or close the tab. The page refuses keys that look secret, but check the prefix yourself anyway: only ever paste a key starting sb_publishable_.

A1.5 Fix it with row-level security (8 min) ​

  1. Back in SQL Editor → New query, open fix.sql, paste all of it, and Run.
  2. Read the result of its last query: the table's RLS status (rls_enabled = true) and the two policies it created. Say each policy out loud in plain words. If you know SQL or Python: the using rule is a filter added to every query, and the with check rule tests every new row.
  3. Re-open Database → Advisors → Security. The "RLS Disabled" error should be gone.

✅ Checkpoint: RLS is on and two policies exist: one for reading public rows, one for adding a valid public row.

A1.6 Re-run the attack and compare (10 min) ​

Go back to the attack page (reconnect if needed) and run every button again. Fill in this table:

Action (public key)Before fixAfter fix
Read all rows
Insert a normal public row
Insert a private row (is_public = false)
Insert a 1,000-character message
Update row #1
Delete newest row

What you should find after the fix: reading shows only the 4 public rows; a normal public insert still works; a private or over-long insert is refused with "new row violates row-level security policy"; update and delete report 0 rows changed and no error.

IMPORTANT

Read the result carefully. There are three different "blocked" answers, and they mean different things:

  • "permission denied" (the page says REFUSED: NO GRANT): the role has no grant for that operation. Lock 1 stopped it.
  • "new row violates row-level security policy" (REFUSED BY RLS): an insert or update broke a policy's rule. Lock 2 stopped it.
  • No error, 0 rows (0 ROWS (FILTERED)): RLS hid every row you weren't allowed to touch, so nothing matched. Also blocked, silently.

So always check how many rows changed, not only whether there was an error. And "0 rows" only proves something if the table really holds rows the public shouldn't see. Labels starting ERROR, and REFUSED BY A COLUMN RULE, aren't security results: they mean a setup problem or bad data.

✅ Checkpoint: your before/after table is filled in, and you can explain why update says "0 rows" instead of an error.

Clean up: keep the practice project if you might reuse it, or delete it from its settings page later. Paste your before/after table into your capstone's SECURITY_CHECKLIST.md under "What I found and fixed".

Troubleshooting (Studio A) ​

  • The attack still works after the fix: you probably pasted a secret key, which skips RLS. Check the prefix: only sb_publishable_ belongs here. The page refuses keys that look secret, but make checking the prefix your habit.
  • "permission denied" before the fix: setup.sql didn't run to the end, so the grants are missing. Run the whole file again; it resets the table.
  • A label starting ERROR: a wrong URL, key, table or column name, or a paused project. Fix the setup and try again; it isn't a security result.
  • The free plan won't let you create another project: delete an old one, or reuse a project you already have after running drop table if exists public.guestbook;.
  • The hosted attack page won't load: open attack.html from the RLS Attack Lab kit on your own computer, or serve the kit folder in a Codespace with python3 -m http.server 8000.

Part B1 — Connect your capstone to Supabase (Core, 40 min) ​

The worked example for feature type (b), a database with access rules. You set up the two locks yourself, attack them, then (Part B2) let the agent wire up the page.

Start on a branch, as in week 12, so the feature reaches main through a pull request:

bash
git switch -c feature/data

Not using a database in your capstone? Do this part anyway on a practice branch you won't merge (git switch -c practice/supabase instead): it's the only time the course walks through it, and saying where authorization is enforced in your app is one of the six skills you must show without AI. If you hit the free plan's project limit, reuse your rls-lab project after running drop table public.guestbook;.

The capstone starter has three files for this. The starter README's feature patterns explain each one:

FileWhat it holdsPublic?
public/config.js (copied from public/config.example.js)Your Project URL and publishable keyYes, by design. Committed
public/lib/db.jsgetDb(), which gives your page one Supabase client. It loads the Supabase library from the jsDelivr CDN (a public server that hosts copies of open-source code, so a page can load it with one import line) and refuses to start with a secret keyYes
supabase/policies.sqlYour tables, their grants and their RLS policies, plus a check query at the endYes. A reviewer reads it to see your rules

B1.1 Decide who may do what (10 min) ​

🔴 AI off for the decision; this is your app's authorization. Before any SQL, fill in this table in SPEC.md (or a comment at the top of supabase/policies.sql), one per table:

RoleReadAddChangeDelete
Anyone (publishable key, not signed in)
Signed-in user (only if you add sign-in)

supabase/policies.sql has two patterns to start from:

  • Pattern A, a public table (messages, like a guestbook): anyone may read every row and add a short one; nobody using the publishable key may change or delete one. Only for data you'd be happy to see on a public notice board.
  • Pattern B, private rows (notes): a signed-in user may read, add, change and delete only their own rows; anyone not signed in gets nothing. Needs sign-in (see Part B3).

If any row could ever be private (a note, an email, a phone number), "anyone may read" is wrong: that's Pattern B.

✅ Checkpoint: you can say your rules in one sentence each, and you know which pattern you'll start from.

B1.2 Create the table, the grants and the policies (15 min) ​

🟡 AI limited: the AI may explain any line or critique your file, but you decide the rules and must be able to explain every line.

  1. Create a Supabase project for your capstone (named after your app) and copy its Project URL and publishable key into your scratch note.
  2. Open supabase/policies.sql. Keep the pattern that matches your B1.1 table, rename the table and columns to fit your app, and delete the other pattern. No data of your own yet? Keep Pattern A exactly as it is.
  3. Find the three parts in what you kept and say each one in plain words: the grant lines (lock 1: may this role use the table at all?), enable row level security, and the create policy statements (lock 2: which rows?). Change the grants and policies so they match your B1.1 table exactly: no grant for anything your table says "no" to.
  4. Paste the whole file into SQL Editor → New query and Run. Read the result of its last query: one line per table, with rls_enabled, its api_grants and its number of policies.

✅ Checkpoint: every table shows rls_enabled = true, its api_grants match your B1.1 table (Pattern A unchanged shows only INSERT and SELECT), and there's at least one policy for each granted operation.

WARNING

Never answer "permission denied" with a bare grant. If your app or an agent hits permission denied for table …, the fix is to add the grant in supabase/policies.sql, together with RLS on and a policy, then re-run the file. A line like grant all on my_table to anon on its own, with RLS off, rebuilds exactly the leak you attacked in Studio A. If an agent proposes it, stop and reject it.

B1.3 Put the URL and publishable key in public/config.js (5 min) ​

  1. In the terminal:

    bash
    cp public/config.example.js public/config.js

  2. Paste your Project URL and publishable key where the file says.

  3. Read the comment at the top of the file. Then write one sentence in your README's "where each key lives" section, in your own words, saying why this key is safe to publish (it's public by design; RLS and the grants protect the data).

✅ Checkpoint: public/config.js holds a key starting sb_publishable_ and nothing starting sb_secret_.

IMPORTANT

This is the "Not every key is a secret" rule from the README. The publishable key goes in public/ and gets committed, because the deployed site needs it. Your LLM key and any secret key stay in .env and in Vercel's environment variables, never in public/.

B1.4 Attack your own table (10 min) ​

Check first: prove the locks hold before any page code depends on them.

  1. Open the RLS attack page again. Connect with your capstone's URL and publishable key, and type your table's name.
  2. Open Testing your own table instead? and describe a row in JSON that matches your columns, for example {"name": "Mallory", "message": "Hello"} for Pattern A.
  3. Try each operation. Everything your B1.1 table says "no" to must come back REFUSED or 0 ROWS. Anything it says "yes" to should be ALLOWED. An ERROR: COLUMN NOT FOUND means your JSON doesn't match the table: fix it and try again.
  4. "0 rows" only proves something if the table holds rows the public shouldn't see. If your rules hide any rows, add one in the Table Editor and check it stays hidden.
  5. Fill in the "authorization is enforced in" line of SECURITY_CHECKLIST.md, for example "in the RLS policies and grants on public.messages, in supabase/policies.sql".
  6. Copy the page's results table into SECURITY_CHECKLIST.md as evidence.
  7. Commit supabase/policies.sql, public/config.js and the checklist on your branch.

✅ Checkpoint: your own attack fails wherever your rules say "no", the grants match your rules, and the checklist names where authorization is enforced.

Part B2 — Connect one feature with the agent (Core, 20 min) ​

🟢 AI on, approvals on. Follow the Safe Loop with its two habits: check first, then teach back. Whatever you don't finish here is the start of your homework.

  1. Check first (3 min). The database call needs the network, so its check is a manual one: write it in TESTS.md before you prompt, for example "Add a message, reload the page, it's still there. Turn off the network in DevTools, add a message, see a friendly error." Any pure logic (checking a message before it's sent, formatting a row) gets an automated test in tests/ first, as in week 11.

  2. Prompt the agent in plan mode first. Change the table and column names to yours:

    text
    Goal: Show the latest messages and let a visitor add one, using getDb() from public/lib/db.js.
Context: Capstone starter. The table public.messages (id, name, message, created_at) exists and
its rules are in supabase/policies.sql. public/config.js holds the project URL and publishable
key. The starter README's "Feature patterns" section shows the read and insert calls.
Constraints: Use only getDb() from public/lib/db.js. Don't edit supabase/policies.sql or
public/config.js. Don't add npm packages or any other key. Show user text with textContent,
never innerHTML. Show a loading message while waiting and a friendly message if a request fails.
Show me the plan and wait for my OK.
Done when: a message I add is still there after a reload, npm test passes, and a failed request
shows a message instead of freezing.

  3. Read the plan, approve it (or correct it), then let it make the change. Read the diff. The calls use await, as in Python's async code: a missing await gives you a Promise instead of rows.

  4. Run your check from step 1 with npm run dev. Run npm test.

  5. Teach back (2 min): in PROMPTS.md, write 2–3 sentences in your own words: what changed and why. Then commit, with an Assisted-by: [tool] line.

  6. Push the branch and open a pull request. You merge it in homework, once it works and you've reviewed it.

✅ Checkpoint: your data survives a reload, npm test passes, and the commit has a teach-back in PROMPTS.md.

TIP

Blank list and a red error in the Console? Check the error's words against the three answers in A1.6. "Permission denied" means a missing grant (fix it in policies.sql); "0 rows" with data in the Table Editor means a missing or too-strict select policy. More: Troubleshooting: Supabase.

Part B3 — Per-user rows, or attack from the Console (If time) ​

Pick one.

  • Per-user rows with Supabase Auth. Make a table where each signed-in user sees only their own rows. Start from the starter's Pattern B (notes), or follow the kit's per-user stretch and write the four policies yourself using (select auth.uid()) = user_id. Turn on Anonymous Sign-Ins (under Authentication; menus move) to test without building a login. This is the pattern for any capstone with private data.
  • Attack from the Console, like a stranger would. Your publishable key is in your live site's source, so anyone can use it from their browser's DevTools Console, not only from the attack page. Ask your assistant to explain each line of a short supabase-js snippet that tries to update and delete every row of your table, then run it on your own live site and read the result using the three answers from A1.6. Expected: "permission denied" for anything you didn't grant.

Troubleshooting (Studio B) ​

  • "permission denied for table …": the table has no grant for that operation. Add it in supabase/policies.sql with RLS and a policy, and re-run the whole file.
  • RLS on, but the page reads nothing: RLS with no policies blocks everyone. Add the select policy your B1.1 table calls for.
  • getDb() refuses to start: public/config.js holds a secret key, or still has the example's placeholder. Paste the sb_publishable_ key.
  • The project is paused: free projects pause after about a week without activity. Open the dashboard and restore it (Troubleshooting: Supabase).
  • The agent wants to edit policies.sql or add a grant: reject that step. You decide the rules; the agent writes page code.

Wrap up ​

  • Commit everything on your branch: supabase/policies.sql, public/config.js, your page code, and the SECURITY_CHECKLIST.md evidence (your before/after table, your own table's results, the "authorization is enforced in" sentence).
  • Update PROMPTS.md template: a teach-back for every agent commit.
  • Do the week 13 exit ticket, AI off (🔴). It's graded on completion, not correctness.
  • Homework: Week 13 homework — Persist it, and prove who can reach it.
