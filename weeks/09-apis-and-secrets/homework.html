Week 9 Homework — Make the micro-app yours, start your pitch ​

Core: about 5½ hours with project time, required. Stretch: optional. Due before next week's Studio A (default 11:59 pm the night before). This homework is the first half of Project 2: An AI Micro-App (brief). Project 2 is graded once, at the end of week 10, with the Project 2 rubric (15% of the course), so this week has no separate homework score. The reflection counts in Assignments; the pitch draft becomes the pitch you submit next week, which counts there too.

AI-use key: 🟢 AI on: use AI, following the Safe Loop · 🟡 AI limited: only in the way the task says · 🔴 AI off: close AI chat and turn off completions. Never paste a key or the contents of .env into any AI tool.

Deliverables checklist ​

Only the reflection goes on Canvas this week; the app is submitted next week.

  • ☐ The app does its own job (system prompt, page text, styling), and the "About this app" section of README.md describes it (task 1)
  • ☐ Your own MAX_INPUT_LENGTH, with one sentence in PROMPTS.md explaining it (task 2)
  • ☐ Empty input, too-long input and a missing key each tried on purpose, with what you saw noted in PROMPTS.md
  • ☐ A first draft of your capstone pitch, kept privately (not in your repository) (task 3)
  • ☐ PROMPTS.md: two or more entries with teach-backs (task 4)
  • ☐ Week 9 reflection on Canvas (🔴 AI off) (task 5)
  • ☐ Everything committed and synced; no .env on github.com; Codespace stopped

Core (required) ​

1. Make it fully yours (about 2 h) ​

🟢 AI on: Copilot Chat in Ask mode, through the Safe Loop. Keep .env closed while Copilot is on.

  1. Finish the job. Improve the system prompt in lib/prompt.js until all three checks from the lab pass, then the page text and styling. Optionally add an input, such as a dropdown for tone; if you do, the server must check it too (in lib/validate.js), because anyone can call /api/ask directly.
  2. Test locally before every push: npm test, then your three checks with npm run dev. A problem found in your Codespace takes minutes to fix; on next week's live site, much longer.
  3. Describe your version. Replace the "About this app" section of README.md with two or three sentences about what your app does and who it's for.
  4. Commit (with an Assisted-by: line if AI helped) and sync.

2. Set your input limit and try each error (about 1 h) ​

🟢 AI on for reading code · 🔴 AI off while .env is open.

Your /api/ask route is public, so the server's input check is what protects your quota.

Choose your limit (15 min). Open public/lib/input.js and set MAX_INPUT_LENGTH to a number that suits your app: a flashcard maker needs room for notes; an "explain like I'm five" box doesn't. Because the browser and the server both import this file, one change updates both the counter and the server check. Add one sentence to PROMPTS.md: what you chose and why.

Try each error on purpose (45 min). For each one, first predict what the page (or terminal) will show and which status code the browser will get; then try it with npm run dev running, and note in PROMPTS.md what you saw:

  • Empty input: press the button with an empty box.

  • Too long: the page's box stops you typing past the limit, so send a long question straight to the server, as a stranger's script would. In a second terminal:

    bash
    node -e "fetch('http://localhost:3000/api/ask',{method:'POST',headers:{'Content-Type':'application/json'},body:JSON.stringify({question:'a'.repeat(5000)})}).then(r=>r.text()).then(console.log)"

  • Missing key (🔴 AI off while .env is open): put a # in front of the LLM_API_KEY line in .env, save, restart the server and ask a question. The page shows a friendly "not set up" message, and the technical detail stays in the terminal. Remove the #, save, close .env and restart. (If you keep your key in Codespaces secrets instead, skip this one and say so in PROMPTS.md.)

Commit: for example Set my input limit. Next week you write automated tests that prove this limit holds.

3. Capstone pitch: a first draft (about 1.5 h) ​

🟡 AI limited: you write the pitch. You may ask an AI to critique it ("What's unclear? What's too big?"), but not to write it.

Your capstone starts in week 11, with an AI agent, from this pitch. The final version is due on Canvas 72 hours before week 11 Studio A, so your instructor can reply Go, Go if you shrink it or Rethink before the studio. Drafting it now means next week's deploy can't squeeze it out.

  1. Read the Capstone brief and browse Capstone Ideas (30 min).
  2. Draft the pitch template (1 h): the problem and the user, a sketch of the main screen, which two or more feature types you'll include (pairs: three or more) from a server-side API call with a hidden key, a database with access rules, a data visualization and an external public API, what's out of scope, and your biggest risk with a plan B.

Keep the draft in a private document, not a public repository. Keep it small: a capstone that works and that you can explain beats a big one that half-works. Pairing up? Agree on it this week.

4. PROMPTS.md (about 30 min) ​

At least two entries this week: your system-prompt work (your checks, the prompt, what you changed) and your input limit with the errors you tried. For every AI-written change you kept, add a teach-back (🔴 AI off: your own words, 2–3 sentences: what changed and why it works; how). Commits where AI helped carry an Assisted-by: line (how). Never paste a key or .env contents into PROMPTS.md: it's public.

5. Reflection on Canvas (about 30 min) ​

🔴 AI off. 150–300 words on Canvas, using the four headings of the reflection template, graded on specifics, not polish (reflection rubric).

Anchor it in one concrete moment: the line in your trace where the key is added, a status code you predicted wrong, or a system-prompt check that failed and what you changed. What do you now understand about the browser/server line that you didn't before Studio A?

Stretch (optional) ​

Pick one. Commit before you start, so you can always go back.

  • Conversation memory. Let the user ask follow-up questions. Keep the conversation in the browser, send the last few messages with each request, and have the server check the total length, not just the latest message. Think about what happens to your quota and to privacy as conversations grow.
  • Streaming replies. Make the answer appear word by word: send "stream": true to the provider, return its stream from api/ask.js, and read it in the browser with response.body.getReader(), adding text with textContent +=. The dev server already passes streams through. Plan it with Copilot first; streaming formats differ slightly between providers.
  • A local model with Ollama. On your own computer (not in a Codespace), install Ollama, pull a small model, run the starter locally (Optional: set up your own computer) and set LLM_BASE_URL=http://localhost:11434/v1. Useful models need a lot of memory; see the Tool Handout. Nothing leaves your machine, and there's no quota. What's the catch?

IMPORTANT

Minimum to keep up. Your micro-app answers a question in your Codespace with your own key, and git status doesn't list .env. Week 10 Studio A deploys exactly that. If it doesn't run yet, bring the exact error to office hours before Studio A.
