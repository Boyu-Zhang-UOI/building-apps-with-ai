Week 5 — Spec First ​

A spec is the prompt for the whole project.

Learning objectives ​

By the end of this week you can:

  1. Write a one-page SPEC.md: problem, user, prioritized user stories, constraints, out of scope, wireframe.
  2. Write WHEN … THE APP SHALL … criteria that a stranger can check by using the app, including edge cases.
  3. Review a classmate's spec: predict the app, find untestable criteria, name a missing edge case.
  4. Run the Goldfish test, and revise the spec from what a fresh chat asked or got wrong.
  5. Explain what an app builder generates behind its preview, and why the "70% problem" makes criteria matter.
  6. Turn criteria into manual tests, and the rules inside them into examples for automated tests.

Before class ​

  • ☐ Finish the week 4 homework.
  • ☐ Choose two or three ideas for Project 1: A Tool I'd Actually Use: single user, data saved in the browser, no login, no real data about other people (idea list, more ideas).
  • ☐ Sketch the main screen of your favorite on paper. Bring the paper or a photo.
  • ☐ Read the example spec, including "Why this spec works".

Key ideas ​

Working on your own? Read this section, then do the lab; the self-paced path replaces the pair activities.

A spec is the prompt for the whole project. Before any prompt, you write one page that says who the tool is for, what it must do, and what it won't do. Everything that reads it later (a classmate, an app builder, a chat assistant and, in week 11, an agent) builds from the same page. Writing well matters: in a 2026 study of 100 students, both writing skill and computing grades predicted how well students vibe-coded (Thorgeirsson et al.).

User stories and priorities. Each feature is written from the user's side: As a student, I want to …, so that …. Mark each one MUST (useless without it), SHOULD or COULD. The MUSTs make your MVP, the minimum viable product: the smallest version that is actually useful. Three to five MUSTs is plenty for Project 1.

Acceptance criteria you can check by using the app. WHEN I press Add with an empty box, THE APP SHALL add nothing and show "Please type a name". The format comes from EARS, which AWS's Kiro tool uses to turn requirements into specs for AI (Kiro). "Easy to use" is not a criterion: nobody can check it. Include edge cases, the unusual situations where bugs live: empty input, duplicates, reloading, a small screen.

Out of scope is a feature. Naming what you are not building (login, sync, charts, dark mode) stops you, and the AI, from wandering. A wireframe, a rough sketch of the screen, does the same for layout.

Say what, not how. If you program, you'll be tempted to put functions or data structures into the spec. Leave them out: a criterion describes what a user sees. Only the Constraints section talks about technology. Your instincts help with boundaries: "40 characters is accepted; 41 is refused" is a sharp criterion.

The Goldfish test. A fresh chat knows nothing about you or your idea, like a goldfish. Paste only your spec into a new chat and ask what it would build and what it would have to ask. Every question is a gap that every later builder and agent will fall into too. Fix the spec, not the chat. Michigan's AI software engineering course uses the same fresh-session test (EGM).

What app builders are. Google AI Studio's Build mode, Bolt, Lovable and v0 turn a description into a whole running app. Behind the preview is a real project: often a framework such as React (a large library that shapes how the app is written), a build step, and sometimes a server, a database and a login. Google documents that AI Studio Build creates React and Node apps and can add a database and login automatically (Google AI Studio docs). Next week you feed one your spec.

The 70% problem. Addy Osmani describes people who get 70% of the way very fast with AI, then stall on the last 30% (edge cases, fixes that break something else) because they have no mental model of the code (Osmani). Your criteria are how you find that 30%. This week you turn them into manual tests, and the rules inside them (checks on input, calculations, dates) into a logic plan of example inputs and expected outputs. Next week those become automated tests, written before the code.

Understanding check ​

The week 5 exit ticket is 🔴 AI off and graded on completion, not correctness. It opens with a look-back question about your week 3 game, answered from memory. Its central question: rewrite a vague requirement as a criterion a stranger could check. To check yourself first:

  • Explain how a stranger would test one of your criteria in under a minute.
  • Name two edge cases in your spec and why each could break.
  • Name one Goldfish question and the line it made you change.
  • Say what an app builder generates behind its preview, and why criteria matter more when you can't read the code.

Homework ​

Core (about 5 hours with project time): finish your spec review; revise SPEC.md and rerun the Goldfish test; manual tests and a logic plan in TESTS.md; your first automated test, failing; your reflection. Details: homework. Project 1 version 1 is due before week 7 Studio A and the final before week 9 Studio A (Project 1 brief, rubric).

If a tool is down ​

If this failsDo this
Your chat assistant (for the Goldfish test)Switch to a fallback in the Tool Handout, open a fresh chat and paste only your SPEC.md
The fresh chat seems to know you alreadyYour assistant's memory is on. Use a temporary chat, or turn memory off (privacy settings)
GitHub is down, or you can't create a repositoryKeep your spec in a document and create the repository later (GitHub basics)
Canvas is downWrite your review in a document and paste it into Canvas when it's back
